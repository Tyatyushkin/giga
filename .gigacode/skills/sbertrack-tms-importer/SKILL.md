# SberTrack TMS Importer

Импортирует тест-кейсы из JSON в SberTrack TSM. Поддерживает различные вариации структуры JSON — гибкий маппинг полей, фоллбэки для отсутствующих полей.

---

## На вход получаешь md файл с описанием теста

Сформируй на его основе json согласно схеме [testcase-schema.json](testcase-schema.json)


## 📥 Входной JSON

Поля могут присутствовать в любой комбинации. Основные варианты:

| Поле | Назначение | Маппинг в TMS |
|---|---|---|
| `title` / `name` / `summary` | Заголовок | `summary` |
| `description` | Описание | `description` (как есть) |
| `goal` | Цель | Раздел `## Цель` в description |
| `preconditions` / `prerequisites` / `pre-conditions` | Предусловия | Раздел `## Предусловия` |
| `postconditions` / `post-conditions` | Послеусловия | Раздел `## Послеусловия` |
| `steps` / `test_steps` / `execution_steps` | Шаги | `steps` |
| `testData` / `test_data` / `data` | Тестовые данные | Раздел `## Тестовые данные` в description |
| `requirements` / `reqs` / `references` | Требования | Включить в description |
| `priority` | Приоритет | Маппинг на TMS priority |
| `id` / `test_case_id` / `key` | Идентификатор | Для проверки дубликатов |
| `gaps` / `gaps_and_questions` | Пробелы | Включить в description |
| `notes` / `comments` / `remarks` | Заметки | Включить в description |

### Формат шагов — три варианта

**Вариант A (с номером):**
```json
{"number": 1, "action": "...", "testData": "...", "expectedResult": "..."}
```

**Вариант B (без номера, с действием и результатом):**
```json
{"action": "...", "result": "...", "data": "..."}
```

**Вариант C (минимальный):**
```json
{"action": "...", "expectedResult": "..."}
```

**Маппинг всегда одинаковый:**
- `action` / `step` / `instruction` → `description` (обязательное)
- `expectedResult` / `result` / `expected` → `result`
- `testData` / `data` / `input` → `data`
- `number` — игнорируется

### Формат тестовых данных

**Массив объектов:**
```json
[{"name": "...", "value": "...", "comment": "..."}]
```
→ Таблица в description

**Массив строк:**
```json
["логин: test", "пароль: 123"]
```
→ Список в description

**Словарь:**
```json
{"login": "test", "password": "123"}
```
→ Список в description

## 📋 Workflow

### 1. Определить пространство

**НЕ ПРОДОЛЖАТЬ** без явного `space_code`.

Спросить пользователя:

```
В какое пространство SberTrack импортировать тест-кейсы? (укажите space_code, например TSTQ)
```

**Ждать явного ответа пользователя.** Не продолжать workflow до получения `space_code`.

### 2. Парсить JSON

Определить структуру входящего JSON:
- Какая структура у `steps`? (A, B или C)
- Есть ли `testData` и в каком формате?
- Какие поля присутствуют?
- Сколько кейсов — один или массив?

### 3. Показать сводку маппинга

**ПЕРЕД созданием** показать пользователю:

```
📋 Сводка импорта:
- Пространство: <space>
- Кейсов: N
- Маппинг:
  - title → summary
  - goal + preconditions → description (маркдаун)
  - steps → test steps (вариант A, 3 полей каждый)
  - priority "Критический" → critical
- Duplicata: нет / найден <code>

Продолжить? (y/n)
```

**Ждать подтверждения** перед созданием первого кейса. После подтверждения — создавать все без дополнительных вопросов.

### 4. Собрать description

Порядок разделов (только если поля присутствуют):

```markdown
## Цель
<goal>

## Предусловия
- <precondition>
- <precondition>

## Тестовые данные
<table или list>

## Требования
<list>

## Послеусловия
- <postcondition>

## Пробелы / Примечания
<list или text>
```

Правила:
- Пустые разделы не включать
- `testData` как объекты → markdown-таблица с тремя колонками
- `testData` как строки → маркированный список
- `testData` как словарь → маркированный список `ключ: значение`
- Разделители между разделами — одна пустая строка

### 5. Маппинг шагов

Для каждого шага:

```json
{"description": "<action>", "result": "<expected>", "data": "<td>"}
```

Правила:
- `description` — всегда, без исключений
- `result` — если `expectedResult` / `result` / `expected` присутствует и не пуст
- `data` — если `testData` / `data` / `input` присутствует и не пуст / не "—"
- Если `data` = "—" или пустая строка — не включать поле в итоговый объект

### 6. Маппинг приоритета

| JSON | TMS |
|---|---|
| "Критический" | `"critical"` |
| "Высокий" | `"high"` |
| "Средний" / "Medium" | `"medium"` |
| "Низкий" / "Low" | `"low"` |
| не указан | (не передавать) |
| другое значение | `"medium"` |

### 7. Проверка дубликатов

**Тул:** `testUnit.search()`

```
testUnit.search({query: 'space = "<space>" AND summary ~ "<title>"'})
```

Если найдено:
- Спросить: обновить существующий, пропустить или создать новый с суффиксом
- Если обновлять — использовать `testUnit.updateTestCase(code="<code>", summary="...", description="...", steps=[...])`

### 8. Создать тест-кейс

**Тул:** `testUnit.createTestCase()`

```
testUnit.createTestCase({
  "space_code": "<space>",
  "summary": "<title>",
  "description": "<description>",
  "steps": [...],
  "type_of_testing": "new"
})
```

### 9. Результат

Вернуть итоговую сводку:

```
📦 Итог импорта:
✅ Создано: N
⏭️ Пропущено (дубли): N
❌ Ошибки: N (<описание>)

Созданные кейсы:
- <code_1>: <title_1>
- <code_2>: <title_2>
```

---

## 📦 Пакетный импорт

Если JSON — массив из N объектов:

1. Показать **одну общую сводку** перед всеми созданиями
2. Создавать последовательно, без промежуточных вопросов
3. Собрать результат по всем кейсам

---

## ⚠️ Гибкость

- Если JSON не содержит `steps` — создать кейс без шагов, шаги можно будет добавить позже через `testUnit.updateTestCase(code="<code>", steps=[...])`
- Если JSON не содержит `testData` — не включать раздел в description
- Если JSON имеет необычные поля — включить их в раздел `## Примечания` в description
- Если `steps` — массив строк (без structured полей):

```json
["Открыть приложение", "Ввести логин", "Нажать Войти"]
```

→ Каждый элемент: `{"description": "<строка>"}`

## 📝 Пример 1 — структура с goal + preconditions + steps variant A

**JSON:**
```json
{
  "id": "TC-001",
  "title": "Вход в систему",
  "goal": "Проверить авторизацию",
  "priority": "Критический",
  "preconditions": ["Пользователь зарегистрирован", "Пароль известен"],
  "steps": [
    {"number": 1, "action": "Открыть страницу входа", "expectedResult": "Форма отображается"},
    {"number": 2, "action": "Ввести логин и пароль", "testData": "admin/1234", "expectedResult": "Форма заполнена"}
  ]
}
```

**Описание:**
```markdown
## Цель
Проверить авторизацию

## Предусловия
- Пользователь зарегистрирован
- Пароль известен
```

**Шаги:**
```json
[
  {"description": "Открыть страницу входа", "result": "Форма отображается"},
  {"description": "Ввести логин и пароль", "data": "admin/1234", "result": "Форма заполнена"}
]
```

## 📝 Пример 2 — минимальная структура, steps variant C

**JSON:**
```json
{
  "name": "Проверка формы",
  "description": "Ручной тест для проверки валидации",
  "steps": [
    {"action": "Заполнить форму с пустым полем", "result": "Ошибка валидации"},
    {"action": "Заполнить все поля", "result": "Форма отправлена"}
  ]
}
```

**Description** — как в JSON, без добавления разделов.

**Шаги:**
```json
[
  {"description": "Заполнить форму с пустым полем", "result": "Ошибка валидации"},
  {"description": "Заполнить все поля", "result": "Форма отправлена"}
]
```
