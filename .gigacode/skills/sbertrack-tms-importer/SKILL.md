# SberTrack TMS Importer

Конвертирует Markdown-файлы E2E тест-кейсов в JSON по схеме **testcase-schema.json** и импортирует в SberTrack TMS через MCP-интеграцию.

---

## 📥 Входные данные

На вход подаются **Markdown-файлы** с тест-кейсами в формате E2E-документации. Каждый `.md` файл содержит **один** кейс.

### Структура Markdown-файла

| Раздел | Синтаксис | Маппинг |
|---|---|---|
| **Название** | `Название: <текст>` в разделе `## Общая информация` | `summary` |
| **ID** | `ID: <текст>` в разделе `## Общая информация` | Имя файла JSON |
| **Цель** | `Цель: <текст>` в разделе `## Общая информация` | Раздел `## Цель` в `description` |
| **Приоритет** | `Приоритет: <текст>` в разделе `## Общая информация` | Раздел `## Приоритет` в `description` |
| **Journey** | `Journey: <код>` в разделе `## Общая информация` | Включить в `labels` |
| **Требования** | `Покрываемые требования: REQ-01, REQ-02, ...` | Раздел `## Трассируемость` в `description` |
| **Предусловия** | `## Предусловия` — маркированный список | Раздел `## Предусловия` в `description` |
| **Тестовые данные** | `## Тестовые данные` — таблица | Раздел `## Тестовые данные` в `description` |
| **Шаги** | `## Шаги` — таблица | `steps[]` |
| **Трассируемость** | `## Трассируемость` — таблица | Раздел в `description` |
| **Постусловия** | `## Постусловия` — маркированный список | Раздел `## Постусловия` в `description` |
| **Выявленные пробелы** | `## Выявленные пробелы` — абзацы/списки | Раздел в `description` |
| **Уточняющие вопросы** | `## Уточняющие вопросы` — абзацы/списки | Раздел в `description` |

---

## 🔧 Workflow

```
MD файлы
   ↓
ШАГ 1: Парсинг Markdown → JSON по схеме
   ↓
ШАГ 2: Валидация JSON
   ↓
ШАГ 3: Запрос space_code у пользователя
   ↓
ШАГ 4: Создание тест-кейса (testUnit.createTestCase)
   ↓
ШАГ 5: Итоговая сводка
```

## ШАГ 1: Парсинг Markdown → JSON

Для каждого MD-файла создайте JSON-объект, соответствующий схеме [testcase-schema.json](testcase-schema.json).

### Извлечение из раздела «Общая информация»

Парсит блок под заголовком `## Общая информация`:

```markdown
Общая информация
ID: TC-J01-00
Название: Регистрация нового пользователя, первое прослушивание...
Цель: Подтвердить, что данные...
Приоритет: Критический
Journey: J01-onboarding-first-play
Вариант от: —
Покрываемые требования: REQ-01, REQ-02, REQ-03, REQ-04
```

| Поле | Действие |
|---|---|
| `ID` | Используется как **имя файла** JSON (например, `TC-J01-00.json`). Не попадает в JSON. |
| `Название` | Значение для **`summary`** |
| `Цель` | Включить в `description` как раздел `## Цель` |
| `Приоритет` | Включить в `description` как раздел `## Приоритет` |
| `Journey` | Включить в **`labels`** массива |
| `Покрываемые требования` | Включить в `description` как раздел `## Трассируемость` (с таблицей, если есть) |
| `Вариант от` | Игнорировать |

### Извлечение разделов в `description`

Каждый раздел из MD копируется в `description` как Markdown-блок. Порядок разделов:

```markdown
## Цель
<текст из раздела "Общая информация">

## Приоритет
<текст из раздела "Общая информация">

## Предусловия
- <условие>
- <условие>

## Тестовые данные
<таблица или текст>

## Постусловия
- <постусловие>

## Трассируемость
<таблица или текст требований>

## Выявленные пробелы
<текст>

## Уточняющие вопросы
<текст>
```

**Правила сборки `description`:**
- Только заполненные разделы (если раздела нет в MD — не включать)
- Разделители между разделами — одна пустая строка
- Таблицы сохраняются как Markdown-таблицы
- Маркированные списки сохраняются как `— <элемент>` или `- <элемент>`

### Извлечение шагов из таблицы `## Шаги`

Таблица имеет 4 колонки:

```markdown
## Шаги

№ | Действие пользователя | Тестовые данные | Ожидаемый результат
---|---|---|---
1 | Открыть приложение «Звук» | — | Отображается экран входа
2 | Ввести номер телефона | +7 999 000-00-11 | В поле ввода отображается номер
```

**Маппинг каждой строки:**

| Колонка | Поле JSON | Правила |
|---|---|---|
| `№` | Игнорируется | Номера шагов не используются |
| `Действие пользователя` | `description` | Обязательное поле, всегда |
| `Тестовые данные` | `data` | Если не `—` и не пусто |
| `Ожидаемый результат` | `result` | Обязательное поле, если есть в таблице |

```json
[
  {"description": "Открыть приложение «Звук»", "result": "Ото displayed экран входа"},
  {"description": "Ввести номер телефона", "data": "+7 999 000-00-11", "result": "В поле ввода отображается номер"}
]
```

**Правила:**
- `description` — всегда обязателен
- `data` — не включать, если значение `—`, пустое или содержит только пробелы
- `result` — если колонка «Ожидаемый результат» есть в таблице, извлекать обязательно

### Извлечение трассируемости (опционально, для `description`)

Таблица `## Трассируемость`:

```markdown
## Трассируемость

Требование | Проверяется шагами
---|---
REQ-01 | 1, 2, 3, 4, 16, 17
REQ-02 | 4, 5, 6
```

Копируется в `description` как Markdown-таблица целиком.

## ШАГ 2: Валидация JSON

Каждый сгенерированный JSON-объект **обязательно** валидируйте по схеме [testcase-schema.json](testcase-schema.json):

**Обязательные поля:**
- `space_code` — пока пустой (заполнится на ШАГ 3)
- `summary` — заполнен из поля «Название»

**Проверки:**
- `steps` — массив, каждый элемент содержит обязательное `description`
- `summary` — не пустая строка, максимум 1000 символов
- `description` — максимум 10000 символов
- `labels` — если есть, массив строк

**При ошибках валидации** — сообщить пользователю и попросить исправить исходный MD.

## ШАГ 3: Запрос space_code

**НЕ ПРОДОЛЖАТЬ** без явного `space_code`.

Спросить пользователя:

> В какое пространство SberTrack импортировать тест-кейсы? (укажите `space_code`, например `TSTQ`)

**Ждать явного ответа.** Подставить `space_code` во все JSON-объекты.

## ШАГ 4: Создание тест-кейса

### Создание нового

```
testUnit.createTestCase({
  "space_code": "<space_code>",
  "summary": "<summary>",
  "description": "<description>",
  "steps": [...],
  "type_of_testing": "new"
})
```

### Обновление существующего

```
testUnit.updateTestCase(
  code="<existing_code>",
  summary="<summary>",
  description="<description>",
  steps=[...]
)
```

## ШАГ 5: Итоговая сводка

Вернуть пользователю:

```
📦 Итог импорта:
✅ Создано: N
❌ Ошибки: N (<описание>)

Созданные кейсы:
- <code_1>: <title_1>
```

## 📦 Пакетный импорт

Если на вход подано **N MD-файлов**:

1. Парсить **все** файлы в JSON
2. Валидировать **все**
3. Запросить `space_code` **один раз**
4. Создать/обновить **все** кейсы
5. Вернуть итоговую сводку по всем файлам

---

## ⚠️ Обработка краевых случаев

| Сценарий | Поведение |
|---|---|
| MD-файл без `## Общая информация` | Ошибка — не удалось извлечь `summary`, пропустить файл |
| MD-файл без `ID` | Использовать имя файла (без `.md`) как имя JSON |
| Кейс без `## Шаги` | Создать без `steps` (поле опционально) |
| Пустая таблица шагов | Создать кейс с пустым массивом `steps: []` |
| Раздел отсутствует в MD | Не включать соответствующий блок в `description` |
| Таблица тестовых данных пуста | Не включать раздел `## Тестовые данные` в `description` |
| Поле «Тестовые данные» в шагах содержит `—` | Не включать поле `data` в шаг |
