# Конвейер циклов дизайн/ревью

Вход: `P` — параллельность, выбранная человеком на шлюзе требований; `MAX_ITERATIONS` — 3 или
значение `--max N`; список journey из `output/suites/`.

Протокол **subagent-briefing** эта процедура использует, но не подключает — его подключает
вызывающая фаза. Каждый вызов `agent` ниже собирается по нему.

## Владение эксклюзивно

Один цикл владеет ровно одной единицей работы и пишет только внутри неё:

| Режим единицы | Чем владеет цикл | Пути, которые он может писать |
|---|---|---|
| `journey` (по умолчанию) | один journey | `output/cases/<J>/`, `output/reviews/<J>-*`, `output/state/<J>.json` |
| `area` | все journey одной функциональной области, по очереди | те же пути, для своих journey |

В режиме `area` группируйте journey по первой строке их поля «Функциональные области»; цикл
начинает следующий journey своей области только после того, как предыдущий достиг `PASS` или
`NEEDS_HUMAN`.

Два цикла не должны никогда писать один и тот же путь. Поэтому критик пишет
`output/state/<J>.json` и никогда агрегатный `output/state.json` — **`output/state.json` пишете
только вы**.

## Батч и очередь

Постройте список работ из journey, упорядоченный по риску — `J01` первым. Первые `P` единиц
образуют **активный батч**; остальные ждут в очереди.

`--journey` сопоставляется как префикс id без учёта регистра (`J01` →
`J01-registration-onboarding-first-play`). Подошло не ровно одно — остановитесь и покажите
список подошедших.

## Счётчик итераций ведёте вы

Номер итерации принадлежит оркестратору, а не критику. Вы передаёте `N` в промпте и в пути
ревью `-iter<N>.md`; критик записывает этот же номер в своё состояние. Читать его как источник
нельзя — вы его сверяете:

```bash
python3 scripts/check_state.py --state output/state/<J>.json --expect-iteration <N>
```

Расхождение — не мелочь: два счётчика, которым разрешено расходиться, — это счётчик, которым
никто не владеет, и решение `iteration >= MAX_ITERATIONS` перестаёт что-либо значить.
Файл с разошедшимся номером считается невалидным, journey уходит в `FAILED`.

## Цепочка

Каждый journey идёт по своей цепочке независимо от остальных:

```
agent(qa-designer) → agent(test-critic) → check_state → решение

1. запускайте всех дизайнеров активного батча в ОДНОМ СООБЩЕНИИ — они идут параллельно.
   Никогда не отправляйте их по одному.
2. КАК ТОЛЬКО вернулся дизайнер конкретного journey — сразу запускайте критика ЭТОГО journey.
   НЕ ЖДИТЕ остальных дизайнеров: journey изолированы, критику нечего от них узнать.
3. когда вернулся критик, проверьте его состояние:
     python3 scripts/check_state.py --state output/state/<J>.json --expect-iteration <N>
   ненулевой код → FAILED, journey покидает батч, ошибка записывается.
   Не читайте вердикт из файла, который не прошёл проверку.
4. по валидному состоянию решите (N — ваш счётчик, сверенный на шаге 3):
     blockers == 0        → PASS,        journey покидает батч
     N >= MAX_ITERATIONS  → NEEDS_HUMAN, journey покидает батч
     иначе                → N += 1, СРАЗУ запускайте дизайнера этого
                            journey на исправление, не дожидаясь других
5. как только слот освободился — берите следующий journey из очереди, не дожидаясь волны
6. повторяйте, пока батч и очередь не опустеют
```

Промпты фикс-итерации — дизайнеру и критику — берите дословно из **subagent-briefing**.

## Почему не волнами

Барьер «все дизайнеры → все критики» оправдан, только когда следующей стадии нужны результаты
всех предыдущих. Здесь не нужны: journey изолированы по построению, критик не читает чужие кейсы.

Замер на трёх journey показал разброс времён дизайнеров **2.94×** (16:37 против 48:54); при
барьере быстрый journey, закончивший свою цепочку за 26:42, начинал бы исправления в 60:45 вместе
с самым медленным — **фора 34 минуты потеряна ни за что**. На каждой итерации заново.

## Решения и учёт

- **Количество блокеров критика — авторитетно.** Не переоценивайте его и не уменьшайте.
- **Никогда не исправляйте кейсы самостоятельно.** Если один цикл застрял, пометьте его `FAILED`
  и дайте остальным завершиться — один неудачный journey не прерывает прогон.
- После каждого изменения статуса выводите одну строку на journey:
  `J01 iter2: BLOCKER 1, MAJOR 3, MINOR 2 → FIX` / `→ PASS` / `→ NEEDS_HUMAN`.
- Агрегируйте `output/state/*.json` в `output/state.json` по мере того, как journey меняют статус:

```json
{ "maxIterations": 3, "parallel": 3, "unit": "journey",
  "journeys": { "J01": {} }, "verdict": "…" }
```

Фаза считается завершённой, когда батч и очередь пусты и каждый journey имеет вердикт
`PASS`, `NEEDS_HUMAN` или `FAILED`.
