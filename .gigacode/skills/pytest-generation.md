# Генерация pytest-тестов

Эта фаза **опциональна и шлюзуется человеком**. Она выполняется только после того, как все циклы
дизайн/ревью завершены: каждый journey получил вердикт `PASS` или `NEEDS_HUMAN`, активный батч
и очередь пусты.

**Границы ответственности.** Здесь описано, что делает оркестратор и что он обещает писателю.
Как писатель пишет код — фикстуры, Allure-разметка, формат его `README.md` — живёт в спеках
`.gigacode/agents/pytest-stub-writer.md` и `.gigacode/agents/browser-test-writer.md`.
Не дублируйте их сюда и не переопределяйте их отсюда.

Протокол **human-gate** эта процедура использует, но не подключает — его подключает вызывающая фаза.

## Шаг 1 — спросить

Вопрос задаётся **один раз**, когда завершены все journey — не по каждому journey, и через
инструмент вопроса по протоколу human-gate, режим A, а не прозой:

- `header`: `Pytest`
- `question`: «Готово N кейсов в Markdown по M journey. Сгенерировать pytest-тесты?»
- варианты: *Да, сгенерировать (рекомендуется)* — «по одному pytest-stub-writer на каждый
  PASS-journey, параллельно» / *Нет, перейти к отчёту* — «кейсы остаются в Markdown».

Если передан флаг `--generate-pytest` — **вопрос пропускается**, ответ считается «да».
Если ответ «нет» — фаза не выполняется, переходите к отчёту.

**При `--no-ask` без `--generate-pytest` значение по умолчанию — «нет»**: отсутствие флага
никогда не означает согласие, а генерация кода — не то действие, которое выполняют, не спросив.
Вопрос записывается в `output/pending.md` по §7 human-gate с этим значением.

## Шаг 2 — кому запускать писателя

Один под-агент `pytest-stub-writer` на каждый journey с **нулём BLOCKER** (вердикт `PASS`).

Journey с вердиктом `NEEDS_HUMAN` писателю не отдаётся — его обрабатывает оркестратор вручную,
тестами с `@pytest.mark.skip`.

Если PASS-journey несколько, все вызовы `agent` уходят **в одном сообщении** — писатели работают
параллельно. Оркестратор дожидается завершения всех.

## Шаг 3 — что писатель читает и пишет

Читает:

| Вход | Путь |
|---|---|
| план journey | `output/suites/<JOURNEY_ID>.md` |
| кейсы, Markdown | `output/cases/<JOURNEY_ID>/TC-*.md` |
| кейсы, JSON | `output/cases/<JOURNEY_ID>/TC-*.json` (если есть) |
| последнее ревью | `output/reviews/<JOURNEY_ID>-iter<N>.md` — источник BLOCKER-пометок |

Пишет — **только** в `output/tests/<JOURNEY_ID>/`, где `<jid>` — номер journey в нижнем регистре
(`J01-onboarding-and-first-play` → `j01`):

| Файл | Содержание | Пишет |
|---|---|---|
| `api_stub_<jid>.py` | детерминированная эмуляция API | stub |
| `test_<jid>.py` | один класс на кейс, один `test_` на шаг | stub |
| `test_browser_<jid>.py` | браузерные тесты — только при `--selenium` | browser |
| `conftest.py` | фикстуры journey | stub, затем **browser дополняет** (`driver`, `base_url`, хук скриншота) |
| `data_<jid>.py` | типизированные константы из таблиц `## Тестовые данные` | stub, затем **browser дополняет** (селекторы, пути страниц) |
| `README.md` | отчёт о генерации и прогоне этого journey | stub, затем **browser дополняет** своим разделом |

Маркеры `J<NN>` регистрировать не нужно: корневой `conftest.py` выводит их из каталогов
`output/tests/`, поэтому `@pytest.mark.J<NN>` работает со `--strict-markers` без правки
`pytest.ini`. Реестр `pytest.ini` под-агенты по-прежнему не трогают.

### Три файла с двумя писателями — исключение, а не недосмотр

`conftest.py`, `data_<jid>.py` и `README.md` пишут оба агента. Это осознанное исключение из
правила «один пишущий на путь», и держится оно **исключительно на очерёдности**:
`browser-test-writer` этого journey стартует только после того, как `pytest-stub-writer`
этого journey завершился (Шаг 5).

Альтернатива — дублировать селекторы в отдельный файл констант — развела бы значения,
которые обязаны совпадать: браузерный тест проверяет тот же шаг того же кейса, что и stub.

**Условие безопасности — очерёдность, и нарушить её нельзя.** Запустив обоих писателей одного
journey параллельно, вы получите гонку на трёх файлах. Параллельность здесь — между journey,
никогда внутри одного.

Каталога `tests/` в корне в этом контракте нет. Реестр маркеров — один на репозиторий, в корневом
`pytest.ini`; под-агенты его не переписывают. Нужен новый маркер — это правка оркестратора, не их.

Отчёт **у каждого journey свой**, в его собственном каталоге. Общего `output/tests/README.md`,
в который дописывают все писатели, быть не должно: это путь с несколькими пишущими, а параллельные
писатели затрут друг друга.

### Почему суффикс `<jid>` обязателен

Pytest импортирует модули по базовому имени файла. Два journey с файлом `test_data.py` дают одно
имя модуля на весь прогон: второй journey получает чужие константы или падает на сборке с
`import file mismatch`.

Отсюда два следствия, оба обязательны:

- суффикс `<jid>` у всех модулей, **кроме** `conftest.py` — его pytest обрабатывает отдельным
  механизмом;
- имя `data_`, а не `test_data_` — файл констант не должен попадать в сборку по маске `test_*.py`.

## Шаг 3.5 — проверить, что писатель произвёл всё

```bash
python3 scripts/check_artifacts.py --journey <JOURNEY_ID> --stage tests
```

Код 1 означает, что писатель оборвался или упёрся в лимит ходов: часть файлов схемы
отсутствует. Доручите ровно недостающее по правилу доката (**journey-pipeline**, «Сбои и
докат»), не переписывая готовое. Сборку из Шага 4 до этого запускать бессмысленно.

## Шаг 4 — проверка сборки по всем journey сразу

Каждый каталог journey по отдельности остаётся зелёным даже при нарушенной схеме имён — коллизия
видна только когда собраны все. Поэтому после завершения **всех** писателей:

```bash
python3 -m pytest output/tests/ --collect-only -q
```

Ошибки импорта здесь означают, что писатель нарушил схему именования. Это его правка, а не ваша:
верните journey писателю, не переименовывайте файлы сами.

## Шаг 5 — браузерные тесты, только по `--selenium`

`browser-test-writer` запускается **исключительно** при флаге `--selenium` и **после** того, как
`pytest-stub-writer` закончил по этому journey. Без флага браузерные тесты не генерируются —
наличие в требованиях описания интерфейса триггером не является.

Флагу нужен адрес стенда: `--base-url <адрес>`, либо адрес зафиксирован в `input/requirements/`.
**Если ни того, ни другого нет — не запускайте `browser-test-writer`**, а внесите вопрос «на каком
стенде выполняются браузерные проверки?» в отчёт.

Подставлять продакшн-адрес продукта самостоятельно запрещено: прогон по адресу, который человек
не назвал для этого прогона, — обращение к постороннему сервису. Собственного адреса у агентов
нет; домен остаётся во входных данных, включая адреса стендов.

Промпт собирайте по протоколу **subagent-briefing**, строка `browser-test-writer`:
к обычным входам писателя добавляется `base_url`.

## Шаг 6 — выход

После завершения всех писателей сообщите:

> «Сгенерировано N тестов, M пропущено. Нужна доработка от человека по K BLOCKER.»

Числа берите из отчётов `output/tests/<JOURNEY_ID>/README.md`, а не из текста ответов агентов.

## Правила, которые оркестратор передаёт писателю

1. **Один тест на шаг.** Функция `test_` тестирует ровно один шаг из одного кейса.
2. **Один класс на кейс.** Никаких добавочных классов вроде `TestEdgeCases` — граничные случаи
   уже пришли как кейсы-варианты.
3. **Пропустить блокеры.** Шаг, помеченный критиком как BLOCKER, даёт тест с `@pytest.mark.skip`;
   в `reason` — ссылка на пробел и номер уточняющего вопроса.
4. **Без вымышленного поведения.** Все ненаблюдаемые ожидания — `skip`.
5. **Данные из констант.** Никаких литералов в тестовом коде и в фикстурах.
6. **API-стаб детерминирован.** Возвращает одно и то же на один и тот же вход — никаких
   flaky-тестов.
7. **Отчёт только по факту прогона.** Каждое число в `README.md` взято из вывода pytest этого
   прогона. Файлы результатов Allure руками не создаются — их порождает только запуск pytest.
   Написанный вручную файл результата — подделка отчёта о прогоне, даже если числа в нём верные.
8. **Граница journey.** Писатель пишет только в `output/tests/<JOURNEY_ID>/` и не трогает
   каталоги других journey, кейсы, планы, ревью и корневой `pytest.ini`.
