# Шлюз требований

Этот шлюз существует потому, что пробел, который никто не выявил, становится вымышленным
ожидаемым результатом через три агента ниже. Никогда не пропускайте его, не смягчайте
и не отвечайте на него от лица человека.

**Вход:** `output/suites/_index.json` и планы в `output/suites/` — то, что написал
`requirements-analyst`.
**Выход:** `output/gate/answers.json`; в ветке «отвечу сейчас» — ещё и `input/requirements/_answers.md`.

Протокол **human-gate** эта процедура использует, но не подключает — его подключает вызывающая
фаза. Если протокола нет в вашем контексте, вы не готовы к Шагу 3.

## Шаг 1 — показать пять списков

Соберите и выведите **полностью**:

1. **Непокрытые требования** — каждый `REQ-XX`, который не попадает ни в один этап journey,
   с причиной.
2. **Пробелы** — требования, которые молчат, противоречат друг другу или неоднозначны,
   дедуплицированные по всем journey, каждый с цитатой исходного текста.
3. **Блокирующие вопросы** — уточняющие вопросы, упорядоченные по количеству этапов и вариантов,
   которые они блокируют.
4. **Этапы без требования** — этапы с маркером `БЕЗ ТРЕБОВАНИЯ`.
5. **Структурные подозрения** — journey с менее чем 5 этапами, менее чем 3 функциональными
   областями, или без передачи данных между этапами. Это ошибки группировки, не факты покрытия —
   пометьте их как таковые.

Не заменяйте список на его количество и не обобщайте элементы. Если список пуст — скажите об этом
явно: «непокрытых требований нет» — это информация, которую человеку нужно знать.

Готовые списки лежат в поле `lists` payload'а из Шага 2 — берите их оттуда, чтобы вывод и вопрос
не разошлись. Порядок шагов при этом не меняется: сначала выполняется Шаг 2, затем печатаются
списки, затем задаётся вопрос.

## Шаг 2 — построить вопросы скриптом

```
python3 scripts/build_gate_questions.py [--parallel N] [--unit journey|area]
```

Передайте флаги прогона, если они были заданы вызывающей фазой. Скрипт читает
`output/suites/_index.json` и пишет `output/gate/questions.json`. Он же решает, какие вопросы
задавать: В1 (покрытие) задаётся всегда, В2 (параллельность) и В3 (владение) подавляются флагами
или единственным journey — см. `skippedQuestions` в payload.

Вопросы вы не сочиняете. Выход `2` означает, что индекс аналитика отсутствует или не парсится —
это ошибка фазы анализа, вернитесь к ней, не придумывайте вопросы вручную.

## Шаг 3 — задать вопрос

Передайте **все** элементы `gateQuestions` в инструмент вопроса по протоколу **human-gate**,
режим A (payload построен скриптом): один вызов, дословно, последнее действие в сообщении.

Запишите ответы в `output/gate/answers.json`, подставляя `value` выбранного варианта
(для «Другого» — текст человека):

```json
{ "coverage": "continue|answer-now|stop", "parallel": 3, "unit": "journey", "answers": [] }
```

## Шаг 4 — ветка по ответу на В1

| `coverage` | Что делать |
|---|---|
| `continue` | перейти к Шагу 5 |
| `answer-now` | ветка ниже |
| `stop` | записать недостающее в `output/report.md` и завершить прогон |

**Ветка «отвечу на вопросы сейчас».** Возьмите `blockingQuestionPrompts` из payload — они уже
упорядочены по количеству заблокированных этапов. Задавайте их по протоколу **human-gate**,
режим B (варианты составляете вы), пачками до 4 вопросов на вызов.

Ответы кладите в `answers` как `{"id": "Q-01", "answer": "…", "source": "option|free"}`.
Затем запишите `input/requirements/_answers.md` (русский, нумерованный, каждый ответ цитирует свой
вопрос), перезапустите аналитика с этим файлом во вводе и **вернитесь к Шагу 2**. Ответы человека
с этого момента — требования.

Повторяйте не более двух раз; на втором проходе не переспрашивайте В2/В3, если ответ на них
уже получен.

## Шаг 5 — проверка перед запуском дизайнеров

**Шаг обязателен, если после шлюза запускаются дизайнеры.** Если вызывающая фаза на шлюзе
останавливается и ничего дальше не запускает (`/e2e:analyze`), Шаг 5 не выполняется — проверять
нечего.

```
python3 scripts/gate_check.py
```

| Код выхода | Что это значит | Что делать |
|---|---|---|
| `0` | шлюз пройден | запускать дизайнеров с `parallel` / `unit` из вывода |
| `1` | ответов нет или они неполны | шлюз нарушен — вернуться к Шагу 3, дизайн не начинать |
| `2` | payload отсутствует | вернуться к Шагу 2 |
| `3` | выбрано не «продолжить» | выполнить `nextAction` из вывода, дизайн не начинать |

Ненулевой код — это не предупреждение. Запуск дизайнеров при коде `1` — прямое нарушение процедуры.

## Режим без вопросов

При `--no-ask` вопросы не задаются: запишите В1/В2/В3 и все блокирующие вопросы в
`output/report.md` под «Требуются решения человека», возьмите `defaults` из payload и пропустите
Шаг 5.
