description: Принять требования, положить их в свой каталог корпуса, проверить, что фабрика их прочтёт, и спросить — запускать ли прогон.
---

Вы принимаете новый корпус требований. Ничего не генерируете и не запускаете сами: задача
этой команды — довести требования до состояния, в котором прогон не сломается на первом же
агенте, и спросить меня, запускать ли его.

Аргументы: {{args}}

- **путь к файлу или каталогу** — взять оттуда;
- **имя корпуса** (`--name knox`) — задать имя явно;
- **ничего** — попросить меня прислать текст требований сообщением; текст, приложенный
  к вызову команды, тоже считается вводом.

## Шаг 1 — куда положить

Каждый корпус живёт в собственном каталоге `input/requirements-<имя>/`. Так уже устроены
`input/requirements-knox/` и `input/requirements-kuper/`; исторический `input/requirements/`
(корпус «Звук») исключение, новые туда не кладите.

Имя корпуса берётся из `--name`, иначе из имени файла, иначе из предметной области первых
строк требований. Только строчные латинские буквы, цифры и дефис.

**Если каталог уже существует — остановитесь и спросите меня**, дописывать в него или завести
новый. Молча дописать чужой корпус — значит смешать два источника требований в одном прогоне,
и разошедшиеся между собой требования обнаружатся тремя агентами ниже как противоречие,
причину которого будет уже не видно.

Файл кладите как есть, ничего не переписывая и не «улучшая». Требования — вход, а не черновик:
переформулировав их, вы подмените источник истины собственным пересказом.

## Шаг 2 — проверить, что фабрика их прочтёт

```
python3 scripts/extract_reqs.py input/requirements-<имя>/ --out /dev/null
```

Скрипт ищет требования двух форм: элемент списка `- **REQ-01.** …` и строку таблицы
`| **BR-001** | … |`. Код `2` означает, что он не нашёл **ни одного** — прогон в таком виде
бессмыслен: аналитик получит текст, в котором нечего пронумеровать, и либо придумает
нумерацию сам, либо вернёт пустой список journey.

Покажите мне вывод целиком. В нём три вещи, на которые стоит посмотреть:

- **сколько записей найдено** — если заметно меньше, чем требований в тексте на глаз,
  часть написана в форме, которой скрипт не знает;
- **какие префиксы встретились** — корпус нумерует не только требования: цели, допущения
  и риски тоже получают id, и `BG-*`, `AS-*`, `RS-*` в требования попадать не должны.
  Если префиксов больше одного, скажите мне, какой набор считать требованиями;
- **повторяющиеся id** — один id на два разных требования означает, что покрытие будет
  считаться неверно, и это правится в источнике, а не позже.

При коде `2` **не предлагайте запуск**. Скажите, что найдено ноль требований, покажите
ожидаемые формы и предложите поправить источник.

## Шаг 3 — ответы человека, если они есть

Если вместе с требованиями пришли ответы на вопросы (файл или текст), положите их рядом
как `input/requirements-<имя>/_answers.md` и проверьте:

```
python3 scripts/extract_reqs.py input/requirements-<имя>/ --answers input/requirements-<имя>/_answers.md --out /dev/null
```

Ответы приравниваются к требованиям, но живут в собственном пространстве id `ANS-NN` — своего
`REQ-NN` они не получают, иначе покрытие вечно числило бы их непокрытыми. Скрипт скажет, если
разделов в файле больше, чем разобранных ответов: значит часть заголовков он не узнал, а
потерять ответ человека нельзя.

Файла ответов может не быть — это нормально, шаг просто пропускается.

## Шаг 4 — спросить, запускать ли прогон

Задайте вопрос через инструмент вопроса по протоколу **human-gate**, режим A: один вызов,
последнее действие в сообщении.

!{python3 scripts/include_skill.py human-gate --level 3}

Поля вопроса передавайте дословно:

- `header`: `Прогон`
- `question`: «Корпус `<имя>` сохранён: N требований, префиксы <список>. Запускать прогон?»
- варианты:
  *Да, запустить сейчас* — «`/e2e:run input/requirements-<имя>/` с вопросами на шлюзах» /
  *Да, автономно* — «то же с `--no-ask`: вопросы копятся в `output/pending.md`, прогон идёт без пауз» /
  *Нет, позже* — «требования сохранены, прогон запускается отдельной командой»

**Если прогон уже идёт — вариант запуска не предлагайте.** Признак: `output/.run` существует,
а в `output/state/` нет файла состояния для каждого journey из `output/suites/_index.json`,
то есть предыдущий прогон не дошёл до конца. Запуск в этот момент вызовет `start_run.py`,
который уберёт артефакты идущего прогона в `output/.previous/` — работа нескольких агентов
пропадёт без предупреждения. Скажите об этом прямо и предложите единственный безопасный
вариант: сохранить требования сейчас, запустить после завершения текущего прогона.

## Шаг 5 — по ответу

- *Да, запустить сейчас* → выполните `/e2e:run input/requirements-<имя>/`;
- *Да, автономно* → `/e2e:run input/requirements-<имя>/ --no-ask`;
- *Нет, позже* → выведите путь к сохранённому корпусу и команду, которой его запустить.

Ничего, кроме сохранения файлов, эта команда не делает: она не трогает `output/`, не создаёт
`output/.run` и не отменяет идущий прогон.
