# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-00
- **Название:** Полный жизненный цикл топологии Knox: деплой, проксирование WebHDFS, удаление
- **Цель:** Подтверждает, что администратор за один сеанс разворачивает топологию demo-e2e через административный API шлюза, её gateway-URL начинает обслуживать WebHDFS (листинг каталога /tmp, запись файла /tmp/demo-e2e.txt, побайтовое чтение того же файла), а после удаления топологии её запись исчезает из реестра и gateway-URL возвращает HTTP 404
- **Приоритет:** Критический
- **Journey:** J01-knox-topology-lifecycle
- **Вариант от:** —
- **Покрываемые требования:** REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06

## Предусловия

- Шлюз Apache Knox запущен, базовый URL https://knox-demo.local:8443 отвечает по TLS. Конкретный адрес стенда и режим проверки сертификата требованиями не заданы — значение выбрано тестом (пробел 5, вопрос 1).
- Демонстрационный LDAP шлюза содержит ровно две учётные записи: admin / admin-password и guest / guest-password (REQ-01). Прогон ведётся от admin, учётная запись guest в этом кейсе не используется.
- Сессия не устанавливается: каждый запрос несёт собственный заголовок Basic-аутентификации (REQ-01).
- Административный API https://knox-demo.local:8443/gateway/admin/api/v1/topologies доступен (REQ-02).
- Топология с именем demo-e2e в ответе GET списка топологий отсутствует — REQ-02: «Перед деплоем топологии с этим именем в списке GET …/topologies нет». Наблюдение подтверждается шагом 1.
- За шлюзом работает сервис WebHDFS, каталог /tmp в HDFS существует и доступен для листинга (REQ-03). Существование каталога до прогона требованиями не гарантировано (пробел 5, вопрос 1).
- Файл /tmp/demo-e2e.txt в HDFS отсутствует. Для второго и последующих прогонов это предусловие не выполняется, пока не получен ответ на вопрос 5 (пробел 7).
- Файл demo-e2e-topology.xml с XML-описанием топологии (провайдер аутентификации ShiroProvider, сервис WEBHDFS) подготовлен на машине, с которой выполняется прогон (REQ-02).
- Все фикстуры кейс создаёт сам на шагах 3 и 8: ни один шаг не потребляет данные, созданные другим journey.

## Постусловия

- Топология demo-e2e отсутствует в ответе GET списка топологий, состав имён реестра совпадает со снимком шага 2 (REQ-06).
- gateway-URL https://knox-demo.local:8443/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS возвращает HTTP 404 при верных учётных данных admin / admin-password (REQ-06).
- Файл /tmp/demo-e2e.txt остаётся в HDFS с содержимым knox e2e payload 2026-08-19: операции удаления файла корпус не описывает (пробел 7, вопрос 5).
- Сессий и токенов после прогона не остаётся: аутентификация выполнялась заголовком Basic на каждом запросе (REQ-01).
- Очистка: для повторяемости прогона требуется удалить /tmp/demo-e2e.txt, но такой операции и её наблюдаемого результата в корпусе нет — до ответа на вопрос 5 второй прогон стартует с уже существующим файлом и попадает в пробел 3.

## Выявленные пробелы

- **Пробел 3 (нумерация плана J01).** Противоречие между параметром и описанным эффектом в REQ-04: запрос назван как «PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true», а результат описан только для отсутствующего файла — «с содержимым в теле создаёт файл: HTTP 201, заголовок `Location` содержит путь файла». Что возвращает тот же запрос на уже существующий путь /tmp/demo-e2e.txt и заменяется ли содержимое, не сказано. Затрагивает шаг 8 при повторном прогоне и постусловия (вопрос 4).
- **Пробел 4 (нумерация плана J01).** Поведение gateway-URL вне установившегося состояния не задано. REQ-02: «Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies` …, а её gateway-URL начинает обрабатывать запросы REQ-03…REQ-05. Перед деплоем топологии с этим именем в списке `GET …/topologies` нет». Про сам gateway-URL до деплоя и внутри 30-секундного окна не сказано ничего, тогда как для симметричной ситуации после удаления REQ-06 наблюдаемое называет явно: «запрос REQ-03 к ней с верными учётными данными возвращает HTTP 404». Затрагивает шаги 4 и 6 (вопрос 3).
- **Пробел 5 (нумерация плана J01).** Стенд не специфицирован до уровня запуска: хост во всех требованиях — плейсхолдер (REQ-02: «PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>»), путь файла — «<путь к файлу>» (REQ-04, REQ-05). Значения https://knox-demo.local:8443, demo-e2e и /tmp/demo-e2e.txt выбраны тестом, а не корпусом. Не сказано также, существует ли каталог /tmp в HDFS до прогона, доверенный ли TLS-сертификат порта 8443 и каков полный текст XML-описания топологии сверх названных провайдера ShiroProvider и сервиса WEBHDFS. Затрагивает предусловия и шаги 1, 3, 6, 8, 9 (вопрос 1).
- **Пробел 6 (новый, выявлен при написании кейса).** HTTP-код операции «GET …/gateway/admin/api/v1/topologies» не задан ни одним требованием. REQ-02 фиксирует только тело: «топология присутствует в ответе `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и `timestamp`)»; REQ-06 — «После удаления топология отсутствует в списке `GET …/topologies`»; REQ-01 переадресует код к операции: «код ответа определяется операцией (REQ-02…REQ-06)». Поэтому шаги 1, 4 и 11 проверяют тело ответа и не проверяют код (вопрос 2).
- **Пробел 7 (новый, выявлен при написании кейса).** Возврат стенда в исходное состояние описан только для реестра топологий (REQ-06: «После удаления топология отсутствует в списке `GET …/topologies`»), а для HDFS не описан вовсе: операции удаления файла в корпусе нет. Файл /tmp/demo-e2e.txt остаётся после прогона, поэтому второй прогон стартует не с чистого состояния шага 7 и попадает в пробел 3. Затрагивает постусловия (вопрос 5).

## Уточняющие вопросы

1. Какие конкретные хост и порт стенда использовать вместо https://knox-demo.local:8443, гарантируется ли существование каталога /tmp в HDFS до прогона, требуется ли отключать проверку TLS-сертификата шлюза на порту 8443 и каков полный текст XML-описания топологии сверх провайдера ShiroProvider и сервиса WEBHDFS? — блокирует предусловия и шаги 1, 3, 6, 8, 9 (вопрос 5 плана J01, пробел 5).
2. Какой HTTP-код возвращает GET …/gateway/admin/api/v1/topologies при верных учётных данных admin / admin-password — до деплоя, после деплоя и после удаления топологии? — блокирует проверку кода ответа на шагах 1, 4 и 11 (новый вопрос, пробел 6).
3. Что возвращает GET …/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS до деплоя топологии и внутри 30-секундного окна после HTTP 200 на PUT, и считается ли ответ внутри окна допустимым промежуточным состоянием, а не дефектом? — блокирует шаги 4 и 6 (вопрос 4 плана J01, пробел 4).
4. Что возвращает повторный PUT …/webhdfs/v1/tmp/demo-e2e.txt?op=CREATE&overwrite=true на уже существующий путь — снова HTTP 201 с заголовком Location, и заменяется ли содержимое файла новым? — блокирует шаг 8 при повторном прогоне и весь кейс TC-J01-03 (вопрос 3 плана J01, пробел 3).
5. Должен ли journey удалять созданный файл /tmp/demo-e2e.txt в постусловии, и какой операцией — в корпусе операции удаления файла нет? — блокирует постусловия и повторяемость TC-J01-00 (вопрос 6 плана J01, пробел 7).
