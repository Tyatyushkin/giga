# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-00
- **Название:** Развёртывание топологии на шлюзе Knox, запись и чтение файла через WebHDFS, удаление топологии
- **Цель:** Подтвердить, что администратор разворачивает топологию через Admin API шлюза, аутентифицированный пользователь через её gateway-URL получает листинг каталога `/tmp`, записывает файл, читает его байт в байт, а после удаления топологии тот же gateway-URL отвечает HTTP 404
- **Приоритет:** Критический
- **Journey:** J01-knox-topology-lifecycle
- **Вариант от:** —
- **Покрываемые требования:** REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06

## Предусловия

- Демонстрационный LDAP шлюза содержит ровно две учётные записи: `admin` / `admin-password` и `guest` / `guest-password`; других учётных записей кейс не заводит (REQ-01)
- Сессия не устанавливается: каждый HTTP-запрос кейса несёт собственный заголовок Basic-аутентификации (REQ-01)
- Топологии с именем `tc-j01-webhdfs` в ответе `GET .../gateway/admin/api/v1/topologies` нет — фиксируется шагами 1–2 (REQ-02)
- Файла `/tmp/tc-j01-2026-08-19.txt` в HDFS нет
- HTTP-клиент имеет сетевой доступ к шлюзу по HTTPS на порт 8443; базовый URL шлюза подставлен из конфигурации стенда — хост требованиями не задан (пробел 1)
- Демонстрационный LDAP и кластер HDFS доступны: WebHDFS-операции обслуживаются (недоступность любого из них — не отказ шлюза)

## Постусловия

- Топология `tc-j01-webhdfs` отсутствует в ответе `GET https://knox-gateway.example:8443/gateway/admin/api/v1/topologies`; её gateway-URL отвечает HTTP 404 на запрос LISTSTATUS (REQ-06)
- Файл `/tmp/tc-j01-2026-08-19.txt` с содержимым `knox e2e payload 2026-08-19` остаётся в HDFS: корпус описывает только `op=CREATE` и `op=OPEN`, операции удаления файла в требованиях нет (пробел 10) — очистка стенда выполняется вне кейса
- Состав демонстрационного LDAP не изменён: две учётные записи из REQ-01, сессий не создано (REQ-01)
- Повторный прогон требует свободного имени топологии и отсутствующего пути файла либо ответов на вопросы 6 и 7 — поведение при повторном деплое и при перезаписи файла требованиями не задано (пробелы 6, 7)

## Выявленные пробелы

- **Пробел 1 (из плана).** Адрес шлюза не задан ни одним требованием. Цитата REQ-02: «Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>` от `admin`…». Схема и порт заданы, хост — нет; значение базового URL в таблице данных подставляется из конфигурации стенда. Блокирует шаги 1–11.
- **Пробел 2 (из плана).** Состав XML-описания топологии не приведён. Цитата REQ-02: «с XML-описанием топологии (провайдер ShiroProvider, сервис WEBHDFS) возвращает HTTP 200». Названы только провайдер и сервис; тело запроса шага 3 в корпусе отсутствует и не придумывается. Блокирует шаг 3.
- **Пробел 5 (из плана).** Не описано состояние в интервале между HTTP 200 на PUT и появлением топологии в реестре. Цитата REQ-02: «Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies`…, а её gateway-URL начинает обрабатывать запросы REQ-03…REQ-05». Что gateway-URL отвечает до этого момента, не сказано, поэтому шаг 5 выполняется строго после подтверждения шага 4.
- **Пробел 6 (из плана).** Повторный деплой на занятое имя не описан. Цитата REQ-02: «Перед деплоем топологии с этим именем в списке `GET …/topologies` нет» — свободное имя задано как предусловие, реакция на PUT по занятому имени не задана. Влияет на повторный прогон шага 3.
- **Пробел 7 (из плана).** Запись поверх существующего файла не описана, хотя параметр перезаписи стоит в самом требовании. Цитата REQ-04: «Запрос `PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true` с содержимым в теле создаёт файл: HTTP 201, заголовок `Location` содержит путь файла». Код ответа и итоговое содержимое при перезаписи не заданы — влияет на повторный прогон шага 6.
- **Пробел 8 (новый).** Не задано, какой именно путь содержит заголовок `Location`. Цитата REQ-04: «HTTP 201, заголовок `Location` содержит путь файла» — HDFS-путь `/tmp/…` или URL-путь `/webhdfs/v1/tmp/…`, не сказано. Шаг 6 проверяет вхождение подстроки `/tmp/tc-j01-2026-08-19.txt`, общей для обоих прочтений.
- **Пробел 9 (новый).** Проверка TLS-сертификата шлюза не описана. Требования задают транспорт («`https://<хост>:8443`»), но не говорят, доверенный ли сертификат на демонстрационном стенде и допустимо ли отключать проверку в клиенте. Влияет на шаги 1–11.
- **Пробел 10 (новый).** Операция удаления файла из HDFS в корпусе отсутствует: REQ-03…REQ-05 описывают только `op=LISTSTATUS`, `op=CREATE` и `op=OPEN`. Постусловие «стенд очищен» средствами требований невыполнимо.
- **Пробел 11 (новый).** Период опроса реестра на шаге 4 не задан. Цитата REQ-02: «Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies`» — задана только верхняя граница; что возвращает `GET …/topologies` до появления записи, не описано.
- **Пробел 16 (новый).** Код ответа операции `GET .../admin/api/v1/topologies` корпусом не задан. Цитата REQ-02: «топология присутствует в ответе `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и `timestamp`)»; цитата REQ-06: «топология отсутствует в списке `GET …/topologies`» — оба требования задают только тело ответа. REQ-01 отсылает за кодом к операции: «код ответа определяется операцией (REQ-02…REQ-06)», а для чтения реестра он там не определён. Шаги 1, 4, 10 проверяют только тело ответа; проверка кода добавляется после ответа на вопрос 8.

## Уточняющие вопросы

1. Какой хост (или полный базовый URL) шлюза использовать в прогоне — блокирует шаги 1–11, все URL кейса (пробел 1).
2. Приведите полное XML-описание топологии, которое считается валидным для `PUT …/admin/api/v1/topologies/tc-j01-webhdfs` (провайдер ShiroProvider, сервис WEBHDFS) — блокирует шаг 3 (пробел 2).
3. Что должно содержаться в заголовке `Location` ответа `op=CREATE`: HDFS-путь `/tmp/tc-j01-2026-08-19.txt` или полный URL шлюза с префиксом `/webhdfs/v1` — блокирует точную проверку шага 6 (пробел 8).
4. Должен ли клиент проверять TLS-сертификат шлюза и какой сертификат установлен на стенде — блокирует однозначную настройку клиента для шагов 1–11 (пробел 9).
5. Что возвращает gateway-URL топологии в интервале между HTTP 200 на PUT (шаг 3) и появлением записи в реестре (шаг 4) — блокирует ужесточение шага 5 и появление отдельного варианта «запрос сразу после деплоя» (пробелы 5, 11).
6. Какой операцией удалять созданный файл `/tmp/tc-j01-2026-08-19.txt` после прогона — блокирует постусловие очистки стенда и повторный прогон на том же пути (пробел 10).
7. Что возвращают `PUT …?op=CREATE&overwrite=true` на существующий путь файла и `PUT …/admin/api/v1/topologies/tc-j01-webhdfs` на уже занятое имя — блокирует повторный прогон шагов 3 и 6 (пробелы 6, 7).
8. Какой HTTP-код возвращает `GET .../admin/api/v1/topologies` при успешном чтении реестра — 200 или иной — блокирует проверку кода ответа в шагах 1, 4, 10 (пробел 16).
