# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-01
- **Название:** Отказ аутентификации на gateway-URL топологии: существующий пользователь с неверным паролем
- **Цель:** Подтвердить, что запрос LISTSTATUS через gateway-URL развёрнутой топологии с существующей учётной записью и неверным паролем возвращает HTTP 401 с текстом `Authentication failed` в теле, а тот же запрос с верным паролем — HTTP 200 и JSON с полем `FileStatuses`
- **Приоритет:** Высокий
- **Journey:** J01-knox-topology-lifecycle
- **Вариант от:** TC-J01-00
- **Покрываемые требования:** REQ-01, REQ-03

## Предусловия

- Действуют все предусловия TC-J01-00: демонстрационный LDAP с учётными записями `admin` / `admin-password` и `guest` / `guest-password`, отсутствие сессий, сетевой доступ к шлюзу по HTTPS на порт 8443 (REQ-01)
- Шаги 1–4 TC-J01-00 выполнены: топология `tc-j01-webhdfs` присутствует в ответе `GET .../gateway/admin/api/v1/topologies` записью с полями `name` и `timestamp`, её gateway-URL обслуживает запросы (REQ-02)
- Точка ветвления — шаг 5 TC-J01-00 (этап 4 плана): тот же запрос LISTSTATUS отправляется с неверным паролем существующей учётной записи
- Файл `/tmp/tc-j01-2026-08-19.txt` этим вариантом не создаётся: шаги 6–11 TC-J01-00 в вариант не входят
- Учётные записи `admin` и `guest` не заблокированы до начала прогона (пробел 12 — блокировка учётной записи корпусом не описана)

## Постусловия

- Топология `tc-j01-webhdfs` остаётся развёрнутой: её запись с полями `name` и `timestamp` присутствует в ответе `GET .../gateway/admin/api/v1/topologies` (REQ-02)
- Файлы в HDFS вариантом не создавались и не изменялись: шаги 1–3 выполняют только `op=LISTSTATUS`
- Состав демонстрационного LDAP не изменён; сессий не создано — каждый шаг нёс собственный заголовок Basic-аутентификации (REQ-01)
- Очистка стенда: топология `tc-j01-webhdfs` удаляется шагами 9–10 TC-J01-00 (`DELETE .../admin/api/v1/topologies/tc-j01-webhdfs` от `admin`, затем контрольный список) — вариант этого не делает

## Выявленные пробелы

- **Пробел 3 (из плана).** Определён только один сценарий отказа аутентификации. Цитата REQ-01: «Любой запрос через шлюз требует Basic-аутентификации против LDAP… Запрос с неверным паролем возвращает HTTP 401, тело ответа содержит текст `Authentication failed`». Запрос вовсе без заголовка Basic-аутентификации и запрос от пользователя, которого нет в LDAP, — это не «запрос с неверным паролем»; их код ответа не описан, поэтому шаги 1–2 берут только существующие учётные записи.
- **Пробел 12 (новый).** Не описано, блокируется ли учётная запись после серии неверных паролей. REQ-01 задаёт реакцию на одиночный запрос («Запрос с неверным паролем возвращает HTTP 401»), но ничего не говорит о счётчике неудачных попыток. Шаг 3 выполняется после двух отказов и предполагает, что верный пароль по-прежнему принимается.
- **Пробел 13 (новый).** Состав тела ответа 401, кроме текста `Authentication failed`, не описан. Цитата REQ-01: «тело ответа содержит текст `Authentication failed`» — есть ли в теле поля JSON и заголовок `WWW-Authenticate`, не сказано, поэтому шаги 1–2 проверяют только заданный текст.
- **Пробел 1 (из плана, унаследован).** Адрес шлюза не задан. Цитата REQ-02: «Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>` от `admin`…». Базовый URL подставляется из конфигурации стенда. Блокирует шаги 1–3.
- **Пробел 2 (из плана, унаследован).** Состав XML-описания топологии не приведён (цитата REQ-02: «с XML-описанием топологии (провайдер ShiroProvider, сервис WEBHDFS) возвращает HTTP 200»), поэтому предусловие «шаги 1–4 TC-J01-00 выполнены» без ответа на вопрос 2 недостижимо.

## Уточняющие вопросы

1. Какой хост (или полный базовый URL) шлюза использовать в прогоне — блокирует шаги 1–3 (пробел 1).
2. Приведите полное XML-описание топологии для `PUT …/admin/api/v1/topologies/tc-j01-webhdfs` — блокирует предусловие варианта, то есть шаги 1–4 TC-J01-00 (пробел 2).
3. Что возвращает шлюз на запрос без заголовка Basic-аутентификации и на запрос от пользователя, которого нет в демонстрационном LDAP: тот же HTTP 401 с телом `Authentication failed` или иное — блокирует расширение шагов 1–2 на эти два случая (пробел 3).
4. Блокируется ли учётная запись после нескольких подряд неверных паролей и через какое время снимается блокировка — блокирует шаг 3, который идёт после двух отказов (пробел 12).
5. Какие ещё элементы обязаны присутствовать в ответе 401 (поля тела, заголовок `WWW-Authenticate`) — блокирует ужесточение проверки шагов 1–2 (пробел 13).
