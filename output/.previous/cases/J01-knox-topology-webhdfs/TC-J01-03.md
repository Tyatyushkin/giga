# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-03
- **Название:** Листинг HDFS через топологию доступен второй учётной записи LDAP — `guest`
- **Цель:** Подтвердить, что операция REQ-03 выполняется от любого аутентифицированного пользователя: тот же листинг `/tmp` от `guest` / `guest-password` возвращает HTTP 200 и JSON с полем `FileStatuses`, как и от `admin`
- **Приоритет:** Средний
- **Journey:** J01-knox-topology-webhdfs
- **Вариант от:** TC-J01-00
- **Покрываемые требования:** REQ-01, REQ-03

## Предусловия

- Наследуются предусловия TC-J01-00 и выполнены его шаги 1–3 (точка ветвления — шаг 4 основного кейса): топология `demo-e2e` развёрнута от `admin`, её запись с полями `name` и `timestamp` присутствует в реестре, gateway-URL обслуживает запросы REQ-03…REQ-05.
- В демонстрационном LDAP есть вторая учётная запись `guest` / `guest-password` (REQ-01); она не использовалась в основном пути.
- Отклонение от основного пути начинается на шаге 4: тот же листинг `/tmp` выполняется от `guest`, а не от `admin`.
- Клиент не хранит сессию — каждый запрос несёт собственный заголовок Basic-авторизации (REQ-01).

## Тестовые данные

| Параметр | Значение | Комментарий |
|---|---|---|
| URL листинга каталога в HDFS | `https://knox-demo.stand.local:8443/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS` | Gateway-URL развёрнутой топологии, каталог `/tmp` из примера REQ-03 (пробел 8, вопрос 1) |
| Логин второй учётной записи | `guest` | REQ-01, вторая запись демонстрационного LDAP |
| Пароль второй учётной записи | `guest-password` | REQ-01 |
| Логин администратора | `admin` | REQ-01, контрольное сравнение на шаге 2 |
| Пароль администратора | `admin-password` | REQ-01 |
| Имя топологии прогона | `demo-e2e` | Развёрнута до начала варианта |

## Шаги

| № | Действие пользователя | Тестовые данные | Ожидаемый результат |
|---:|---|---|---|
| 1 | Запросить листинг каталога `/tmp` через gateway-URL топологии `demo-e2e` с Basic-заголовком учётной записи `guest` | `https://knox-demo.stand.local:8443/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS`, `guest` / `guest-password` | HTTP 200, тело ответа — JSON с полем `FileStatuses` (REQ-01, REQ-03) |
| 2 | Повторить тот же листинг каталога `/tmp` через gateway-URL топологии `demo-e2e` с Basic-заголовком учётной записи `admin` | `https://knox-demo.stand.local:8443/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS`, `admin` / `admin-password` | HTTP 200, тело ответа — JSON с полем `FileStatuses` (REQ-01, REQ-03): код ответа и наличие поля совпадают с шагом 1, то есть результат операции REQ-03 одинаков для обеих учётных записей LDAP |

## Постусловия

- Топология `demo-e2e` остаётся развёрнутой, её запись с полями `name` и `timestamp` присутствует в реестре `GET …/admin/api/v1/topologies`.
- Содержимое каталога `/tmp` в HDFS не изменялось: обе операции варианта — только чтение (`op=LISTSTATUS`).
- Очистка: топологию `demo-e2e` требуется снять запросом `DELETE …/admin/api/v1/topologies/demo-e2e` от `admin` (шаг 8 основного кейса TC-J01-00), иначе предусловие REQ-02 для следующего прогона нарушено.

## Выявленные пробелы

- **Пробел 3.** REQ-02 и REQ-06 явно требуют учётную запись `admin` («от `admin`»), а REQ-01 описывает LDAP с двумя записями и определяет только случай неверного пароля. Реакция админского API на запрос от `guest` с верным паролем — 401, 403 или выполнение операции — не определена, поэтому вариант ограничен операцией REQ-03, где формулировка «от аутентифицированного пользователя» однозначна.
- **Пробел 11 (новый).** REQ-03 определяет для аутентифицированного пользователя только код HTTP 200 и наличие поля `FileStatuses`. Совпадает ли содержимое листинга для `guest` и для `admin` (одинаковый ли набор записей внутри `FileStatuses`), корпус не описывает, поэтому шаг 2 сравнивает лишь код ответа и наличие поля.
- **Пробел 8.** Адрес стенда и каталог HDFS даны корпусом только шаблоном и примером; значение `https://knox-demo.stand.local:8443` подставлено прогоном.

## Уточняющие вопросы

1. Что возвращает админский API (`PUT` и `DELETE …/admin/api/v1/topologies/demo-e2e`) на запрос от `guest` с верным паролем — 401, 403 или выполнение операции? Блокирует расширение варианта за пределы шага 1: сейчас проверяется только операция REQ-03.
2. Должно ли содержимое поля `FileStatuses` совпадать для `guest` и `admin` при одинаковом каталоге? Блокирует усиление шага 2 до сравнения тел ответов, а не только кода и наличия поля.
3. Что возвращают через gateway-URL операции REQ-04 (`op=CREATE`) и REQ-05 (`op=OPEN`) от `guest` — те же HTTP 201 и HTTP 200 либо отказ по правам? Блокирует добавление шагов на запись и чтение файла от второй учётной записи.
4. Какой адрес стенда подставлять вместо шаблонного хоста в адресах требований? Блокирует оба шага варианта (пробел 8).
