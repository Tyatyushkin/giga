# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-00
- **Название:** Развернуть топологию Knox, записать и прочитать файл в HDFS через её gateway-URL, снять топологию
- **Цель:** Подтвердить, что администратор разворачивает топологию через админский API шлюза, работает через её gateway-URL с WebHDFS (листинг, запись, побайтово совпадающее чтение) под Basic-аутентификацией LDAP и снимает топологию так, что её запись исчезает из реестра, а gateway-URL отвечает HTTP 404
- **Приоритет:** Критический
- **Journey:** J01-knox-topology-webhdfs
- **Вариант от:** —
- **Покрываемые требования:** REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06

## Предусловия

- Демонстрационный LDAP шлюза содержит две учётные записи: `admin` / `admin-password` и `guest` / `guest-password` (REQ-01). Основной путь целиком выполняется от `admin`.
- Клиент не хранит сессию: каждый запрос несёт собственный заголовок Basic-авторизации (REQ-01). Отдельного шага входа в сценарии нет — аутентификация проверяется на каждом запросе.
- Топология с именем `demo-e2e` на шлюзе не развёрнута: записи с `name` = `demo-e2e` в ответе `GET …/admin/api/v1/topologies` нет. Это предусловие задано самим REQ-02 («Перед деплоем топологии с этим именем в списке `GET …/topologies` нет») и проверяется шагом 1.
- Файл `/tmp/demo-e2e.txt` в HDFS не создан. Каталог `/tmp` в HDFS существует и доступен на чтение и запись — без этого шаги 4–7 неисполнимы (пробел 8, вопрос 1).
- Шлюз Knox запущен, слушает HTTPS на порту 8443, сервис WEBHDFS за шлюзом доступен. Сертификат стенда самоподписанный, клиент настроен на его приём — техническая предпосылка прогона, требованиями не описанная и в наблюдаемые результаты не входящая.
- XML-описание топологии `demo-e2e.xml` подготовлено заранее: провайдер ShiroProvider, сервис WEBHDFS (REQ-02).

## Постусловия

- Топология `demo-e2e` на шлюзе снята: записи с `name` = `demo-e2e` в ответе `GET …/admin/api/v1/topologies` нет (REQ-06), реестр вернулся к снимку шага 1.
- Gateway-URL `https://knox-demo.stand.local:8443/gateway/demo-e2e` не обслуживает запросы: листинг `/tmp` с верными учётными данными `admin` отвечает HTTP 404 (REQ-06).
- Файл `/tmp/demo-e2e.txt` с содержимым `knox-e2e-payload-2026-08-19` создан через шлюз на шаге 5. Что с ним происходит после снятия топологии, требованиями не определено (пробел 7, вопрос 7) — постусловие остаётся открытым.
- Очистка для повторного прогона: предусловие REQ-02 («Перед деплоем топологии с этим именем в списке `GET …/topologies` нет») выполняется само после шага 8. Удаление файла `/tmp/demo-e2e.txt` корпусом не описано — способ очистки HDFS вне рамок требований, до ответа на вопрос 7 повторный прогон стартует с уже существующим файлом.
- Учётные записи LDAP не изменялись, сессия не создаётся: каждый запрос нёс собственный заголовок Basic-авторизации (REQ-01).

## Выявленные пробелы

- **Пробел 1.** REQ-02 описывает ответ реестра только по содержимому: «топология присутствует в ответе `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и `timestamp`)» — HTTP-код этого запроса не назван. REQ-01 отсылает за кодом к операции: «код ответа определяется операцией (REQ-02…REQ-06)», но для листинга топологий кода нет нигде. Шаги 1, 3 и 9 наблюдают этот ответ и проверяют только его содержимое.
- **Пробел 2.** REQ-02 задаёт «Перед деплоем топологии с этим именем в списке `GET …/topologies` нет» как предусловие и молчит о реакции на его нарушение: что вернёт `PUT …/topologies/demo-e2e`, если топология с этим именем уже развёрнута, не определено. Это делает шаг 2 воспроизводимым только при гарантированно чистом реестре, подтверждённом шагом 1.
- **Пробел 5.** Реакция на обращение к несуществующим ресурсам не определена: REQ-05 описывает `op=OPEN` только для файла, загруженного в REQ-04, а REQ-06 — только удаление существующей топологии. Что вернут `op=OPEN` по несуществующему пути и `DELETE …/topologies/demo-e2e` для неразвёрнутой топологии, корпус не говорит — негативные ветки шагов 6 и 8 непроверяемы.
- **Пробел 6.** REQ-04 содержит параметр `overwrite=true`, но описывает только создание: «с содержимым в теле создаёт файл: HTTP 201», а REQ-05 привязывает эталон сравнения к «загруженному в REQ-04». Для повторной записи по тому же пути эталон шага 7 становится неоднозначным, поэтому шаг 5 выполняется ровно один раз за прогон.
- **Пробел 7.** REQ-06 описывает последствия удаления топологии только для реестра и gateway-URL: «топология отсутствует в списке `GET …/topologies`, а запрос REQ-03 к ней с верными учётными данными возвращает HTTP 404». Судьба файла `/tmp/demo-e2e.txt`, записанного через эту топологию на шаге 5, не определена — затронуты постусловия и повторяемость прогона.
- **Пробел 8.** Все адреса корпуса даны шаблоном вида `https://…:8443/…`, конкретный адрес стенда не задан; доступный на запись путь HDFS тоже не задан — `/tmp` фигурирует только как пример листинга в REQ-03. Значения `https://knox-demo.stand.local:8443` и `/tmp/demo-e2e.txt` в таблице данных взяты как параметры прогона и подлежат подтверждению (вопрос 1).

## Уточняющие вопросы

1. Какой адрес стенда подставлять вместо шаблонного хоста в адресах требований и какой путь HDFS доступен на запись для файла прогона (подтверждается ли `/tmp` из примера REQ-03)? Блокирует шаги 1–10: до ответа значения `https://knox-demo.stand.local:8443` и `/tmp/demo-e2e.txt` остаются параметрами прогона, а не данными из требований.
2. Какой HTTP-код возвращает `GET …/admin/api/v1/topologies` при верных учётных данных `admin`? Блокирует шаги 1, 3 и 9 — в каждом из них ответ реестра является наблюдаемым, и сейчас проверяется только тело.
3. Что возвращает `PUT …/admin/api/v1/topologies/demo-e2e`, если топология с этим именем уже развёрнута — HTTP 200 с перезаписью, ошибку или иной код? Блокирует шаг 2 на повторном прогоне и определяет, нужен ли отдельный вариант на повторный деплой.
4. Остаётся ли файл `/tmp/demo-e2e.txt` в HDFS после удаления топологии, через которую он был записан? Блокирует раздел «Постусловия» и повторяемость прогона.
5. Что возвращают `GET …?op=OPEN` для несуществующего файла и `DELETE …/admin/api/v1/topologies/demo-e2e` для неразвёрнутой топологии? Блокирует негативные варианты к шагам 6 и 8.
6. Какое содержимое возвращает `op=OPEN` после повторной записи по тому же пути с `overwrite=true` — последнее загруженное или исходное? Блокирует вариант на повторную запись к шагу 5 и однозначность эталона шага 7.
