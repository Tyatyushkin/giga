# E2E тест-кейс

## Общая информация

- **ID:** TC-J01-01
- **Название:** Деплой топологии с неверным паролем администратора отсекается шлюзом до админского API
- **Цель:** Подтвердить, что `PUT …/admin/api/v1/topologies/demo-e2e` с логином `admin` и неверным паролем возвращает HTTP 401 с текстом `Authentication failed` в теле, а топология в реестре не появляется
- **Приоритет:** Критический
- **Journey:** J01-knox-topology-webhdfs
- **Вариант от:** TC-J01-00
- **Покрываемые требования:** REQ-01, REQ-02

## Предусловия

- Наследуются предусловия TC-J01-00 до точки ветвления (шаг 2 основного кейса): шлюз слушает HTTPS на порту 8443, демонстрационный LDAP содержит `admin` / `admin-password` и `guest` / `guest-password`, XML-описание `demo-e2e.xml` подготовлено (провайдер ShiroProvider, сервис WEBHDFS).
- Топология `demo-e2e` не развёрнута: записи с `name` = `demo-e2e` в реестре нет (предусловие REQ-02), что подтверждается шагом 1.
- Отклонение от основного пути начинается на шаге 2: тот же запрос деплоя отправляется с логином `admin` и неверным паролем `admin-password-wrong`.
- Клиент не хранит сессию — каждый запрос несёт собственный заголовок Basic-авторизации (REQ-01).

| URL реестра топологий | `https://knox-demo.stand.local:8443/gateway/admin/api/v1/topologies` | Адрес стенда подставлен прогоном (пробел 8, вопрос 1) |
| Логин администратора | `admin` | REQ-01 |

| Имя топологии прогона | `demo-e2e` | Имя, которое не должно появиться в реестре |
| XML-описание топологии | `demo-e2e.xml` | Провайдер ShiroProvider, сервис WEBHDFS (REQ-02) |

## Постусловия

- Топология `demo-e2e` не развёрнута: реестр `GET …/admin/api/v1/topologies` не содержит записи с `name` = `demo-e2e`, состояние шлюза совпадает со снимком шага 1.
- Gateway-URL `https://knox-demo.stand.local:8443/gateway/demo-e2e` не создавался, файлы в HDFS не записывались — очистка после прогона не требуется.
- Предусловие REQ-02 для основного кейса TC-J01-00 остаётся выполненным: имя `demo-e2e` свободно.

## Выявленные пробелы

- **Пробел 4.** REQ-01 определяет только случай неверного пароля: «Запрос с неверным паролем возвращает HTTP 401, тело ответа содержит текст `Authentication failed`». Что вернёт шлюз на запрос вовсе без заголовка `Authorization` и на запрос от несуществующего в LDAP пользователя, не определено, хотя первая фраза требования шире: «Любой запрос через шлюз требует Basic-аутентификации против LDAP». Поэтому шаг 2 проверяет ровно одну ветку — верный логин с неверным паролем.
- **Пробел 1.** HTTP-код ответа `GET …/topologies` требованиями не задан (REQ-02 описывает только содержимое ответа), поэтому шаги 1 и 3 проверяют только тело списка.
- **Пробел 9 (новый).** REQ-01 не задаёт конкретную строку неверного пароля и не описывает, отличается ли реакция шлюза на пустой пароль от реакции на непустой неверный. Значение `admin-password-wrong` выбрано прогоном как строка, отсутствующая в демонстрационном LDAP.

## Уточняющие вопросы

1. Что возвращает шлюз на запрос без заголовка `Authorization` и на запрос от отсутствующего в LDAP пользователя — тот же HTTP 401 с текстом `Authentication failed` или иной ответ? Блокирует добавление этих двух веток к шагу 2.
2. Отличается ли реакция шлюза на пустой пароль от реакции на непустой неверный пароль? Блокирует выбор граничного значения для шага 2: сейчас используется непустая строка `admin-password-wrong`.
3. Какой HTTP-код возвращает `GET …/admin/api/v1/topologies` при верных учётных данных `admin`? Блокирует шаги 1 и 3 — в них проверяется только тело ответа.
4. Какой адрес стенда подставлять вместо шаблонного хоста в адресах требований? Блокирует все шаги: значение `https://knox-demo.stand.local:8443` взято как параметр прогона (пробел 8).
