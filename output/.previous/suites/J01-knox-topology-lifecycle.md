# E2E Journey / Suite Plan

## Общая информация

- **ID journey:** J01-knox-topology-lifecycle
- **Название:** Развернуть топологию шлюза, записать и прочитать файл через WebHDFS, удалить топологию
- **Цель journey:** Подтвердить, что администратор может развернуть топологию на шлюзе Knox, аутентифицированный пользователь через неё записывает и читает файл в HDFS без искажения содержимого, а после удаления топологии тот же путь перестаёт обслуживаться
- **Приоритет:** Критический
- **Функциональные области:** аутентификация, администрирование топологий, проксирование WebHDFS, жизненный цикл топологии
- **Покрываемые требования:** REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06

## Индекс требований

| Анкор | Формулировка требования | Источник (файл, раздел) |
|---|---|---|
| REQ-01 | Любой запрос через шлюз требует Basic-аутентификации против LDAP. В демонстрационном LDAP две учётные записи: `admin` / `admin-password` и `guest` / `guest-password`. Запрос с неверным паролем возвращает HTTP 401, тело ответа содержит текст `Authentication failed`. Запрос с верными учётными данными передаётся сервису; код ответа определяется операцией (REQ-02…REQ-06) | knox-demo.md § Аутентификация |
| REQ-02 | Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>` от `admin` с XML-описанием топологии (провайдер ShiroProvider, сервис WEBHDFS) возвращает HTTP 200. Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и `timestamp`), а её gateway-URL начинает обрабатывать запросы REQ-03…REQ-05. | REQ-03 | Запрос `GET https://<хост>:8443/gateway/<имя>/webhdfs/v1/tmp?op=LISTSTATUS` от аутентифицированного пользователя возвращает HTTP 200 и JSON с полем `FileStatuses` | knox-demo.md § Проксирование WebHDFS |
| REQ-04 | Запрос `PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true` с содержимым в теле создаёт файл: HTTP 201, заголовок `Location` содержит путь файла | knox-demo.md § Проксирование WebHDFS |
| REQ-05 | Запрос `GET …/webhdfs/v1/<путь к файлу>?op=OPEN` возвращает HTTP 200 и содержимое, байт в байт совпадающее с загруженным в REQ-04 | knox-demo.md § Проксирование WebHDFS |
| REQ-06 | Запрос `DELETE …/admin/api/v1/topologies/<имя>` от `admin` возвращает HTTP 200. После удаления топология отсутствует в списке `GET …/topologies`, а запрос REQ-03 к ней с верными учётными данными возвращает HTTP 404 | knox-demo.md § Жизненный цикл топологии |

## Начальное состояние

- Аккаунт: демонстрационный LDAP шлюза содержит ровно две учётные записи — `admin` / `admin-password` и `guest` / `guest-password` (REQ-01); других учётных записей journey не заводит
- Авторизация: сессия не устанавливается — каждый запрос несёт собственный заголовок Basic-аутентификации (REQ-01)
- Данные пользователя: топологии с именем, которое выберет этап 1, в ответе `GET …/topologies` нет (REQ-02); файла, который создаст этап 5, в HDFS нет
- Устройство / сеть: HTTP-клиент имеет сетевой доступ к шлюзу по порту 8443 (HTTPS); адрес шлюза в корпусе не назван — см. пробел 1

Значения, которые journey выбирает сам и которые не являются поведением системы: имя топологии,
путь и содержимое файла в HDFS. Их конкретные значения фиксирует этап 1 и этап 5, и все
последующие этапы используют ровно их.

## Основной путь

Администратор `admin` запрашивает список топологий шлюза и убеждается, что имени, выбранного
для проверки, в нём нет; отправляет `PUT` на `…/admin/api/v1/topologies/<имя>` с XML-описанием
топологии (провайдер ShiroProvider, сервис WEBHDFS) и получает HTTP 200; в течение 30 секунд
повторяет `GET …/topologies` и находит там запись с полями `name` и `timestamp` для своего имени.
Дальше работа идёт через gateway-URL этой топологии: `GET …/webhdfs/v1/tmp?op=LISTSTATUS`
возвращает HTTP 200 и JSON с полем `FileStatuses`; `PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true`
с содержимым в теле возвращает HTTP 201 и заголовок `Location`, содержащий путь файла;
`GET …/webhdfs/v1/<путь к файлу>?op=OPEN` возвращает HTTP 200 и то же содержимое байт в байт.
Затем `admin` отправляет `DELETE …/admin/api/v1/topologies/<имя>`, получает HTTP 200 и видит,
что имени топологии в ответе `GET …/topologies` больше нет; повторный запрос LISTSTATUS к тому же
gateway-URL с верными учётными данными возвращает HTTP 404. Становится кейсом `TC-J01-00`.

## Зависимости и риски

- Этапы строго упорядочены: gateway-URL из этапов 4–6 существует только между HTTP 200 на этапе 2
  и HTTP 200 на этапе 7. Запуск этапа 4 раньше подтверждения этапа 3 попадает в интервал,
  поведение в котором не определено (пробел 5).
- Временное окно: REQ-02 даёт «не позднее чем через 30 секунд» на появление топологии в реестре.
  Этап 3 — это опрос до появления записи в пределах этого окна, а не единичный запрос.
- Внешние системы: демонстрационный LDAP (учётные записи из REQ-01) и кластер HDFS, отвечающий
  на WebHDFS-операции. Недоступность любого из них ломает journey начиная с этапа 4, и это
  не отказ шлюза.
- Journey изменяет состояние стенда дважды: разворачивает и удаляет топологию (этапы 2 и 7),
  создаёт файл в `/tmp` (этап 5). Файл после этапа 8 не удаляется — требования не описывают
  операцию удаления файла, поэтому повторный прогон должен выбирать новый путь файла либо
  опираться на `overwrite=true` из REQ-04, поведение которого не определено (пробел 7).
- Транспорт — HTTPS на порту 8443. Как проверяется сертификат шлюза, требования не описывают.

## Выявленные пробелы

- **Пробел 1.** Адрес шлюза не задан ни одним требованием — во всех формулировках стоит
  плейсхолдер. Цитата REQ-02: «Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>`
  от `admin`…». Порт (8443) и схема (HTTPS) заданы, хост — нет. Без него ни один шаг кейса
  не может назвать конкретный URL. Блокирует все этапы.
- **Пробел 2.** Состав XML-описания топологии не приведён. Цитата REQ-02: «с XML-описанием
  топологии (провайдер ShiroProvider, сервис WEBHDFS) возвращает HTTP 200». Названы только
  провайдер и сервис; тело запроса дизайнер записать не может, а придумывать его нельзя.
  Блокирует этап 2.
- **Пробел 3.** Определён только один сценарий отказа аутентификации. Цитата REQ-01: «Любой
  запрос через шлюз требует Basic-аутентификации против LDAP… Запрос с неверным паролем
  возвращает HTTP 401, тело ответа содержит текст `Authentication failed`». Запрос вовсе без
  заголовка Basic-аутентификации и запрос от пользователя, которого нет в LDAP, — это не
  «запрос с неверным паролем», и их код ответа не описан.
- **Пробел 4.** Не описано, что возвращают административные операции неадминистративному
  пользователю. Цитаты: REQ-02 — «Запрос `PUT …/topologies/<имя>` от `admin` … возвращает
  HTTP 200»; REQ-06 — «Запрос `DELETE …/admin/api/v1/topologies/<имя>` от `admin` возвращает
  HTTP 200». Обе формулировки называют только `admin`. REQ-01 при этом отсылает за кодом ответа
  обратно к ним: «код ответа определяется операцией (REQ-02…REQ-06)» — то есть для `guest`
  на этих операциях код ответа не определён нигде.
- **Пробел 5.** Не описано состояние в интервале между HTTP 200 на PUT и появлением топологии.
  Цитата REQ-02: «Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies`…,
  а её gateway-URL начинает обрабатывать запросы REQ-03…REQ-05». Что gateway-URL отвечает
  до этого момента — не сказано.
- **Пробел 6.** Не описан повторный деплой топологии с уже занятым именем. Цитата REQ-02:
  «Перед деплоем топологии с этим именем в списке `GET …/topologies` нет» — требование задаёт
  свободное имя как предусловие, но не говорит, что произойдёт при PUT на существующее имя.
- **Пробел 7.** Не описана запись поверх существующего файла, хотя параметр перезаписи стоит
  в самом требовании. Цитата REQ-04: «Запрос `PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true`
  с содержимым в теле создаёт файл: HTTP 201, заголовок `Location` содержит путь файла».
  Описан только случай создания; код ответа, `Location` и итоговое содержимое при перезаписи
  существующего файла не заданы.

## Уточняющие вопросы

1. Какой хост (или полный базовый URL) шлюза использовать в прогоне — блокирует этапы 1–8
   и оба варианта TC-J01-01, TC-J01-02 (пробел 1).
2. Приведите XML-описание топологии, которое считается валидным для PUT: полное тело запроса
   с провайдером ShiroProvider и сервисом WEBHDFS — блокирует этап 2 (пробел 2).
3. Что возвращает шлюз на запрос без заголовка Basic-аутентификации и на запрос от пользователя,
   которого нет в демонстрационном LDAP: тот же HTTP 401 с телом `Authentication failed` или
   что-то иное — блокирует появление отдельного варианта к этапу 4 (пробел 3).
4. Что возвращают `PUT …/topologies/<имя>` и `DELETE …/topologies/<имя>` под учётной записью
   `guest` — блокирует появление варианта к этапам 2 и 7 (пробел 4).
5. Что возвращает gateway-URL топологии в интервале между HTTP 200 на PUT и её появлением
   в `GET …/topologies` — блокирует ужесточение этапа 4 и появление варианта «запрос сразу
   после деплоя» (пробел 5).
6. Что возвращает `PUT …/topologies/<имя>` на имя, которое уже присутствует в
   `GET …/topologies` — блокирует появление варианта к этапу 2 (пробел 6).
7. Что возвращает `PUT …?op=CREATE&overwrite=true` на существующий путь: тот же HTTP 201
   с заголовком `Location`, и совпадает ли последующее чтение с новым содержимым — блокирует
   появление варианта к этапам 5–6 и повторный прогон journey на том же пути файла (пробел 7).
