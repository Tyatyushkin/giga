# E2E Journey / Suite Plan

## Общая информация

- **ID journey:** J01-knox-topology-lifecycle
- **Название:** Полный жизненный цикл топологии Knox: деплой, проксирование WebHDFS, удаление
- **Цель journey:** Администратор шлюза Apache Knox за один сеанс разворачивает новую топологию, через её gateway-URL записывает и читает файл в HDFS, после чего удаляет топологию и убеждается, что её URL больше не обслуживается.
- **Приоритет:** Критический
- **Функциональные области:** Аутентификация, Администрирование топологий, Проксирование WebHDFS, Жизненный цикл топологии
- **Покрываемые требования:** REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06

## Начальное состояние

- Аккаунт: демонстрационный LDAP шлюза содержит ровно две учётные записи — `admin` / `admin-password` и `guest` / `guest-password` (REQ-01). Journey ведётся от `admin`; `guest` используется только вариантом TC-J01-02.
- Авторизация: сессии нет и не предполагается — каждый запрос несёт собственный заголовок Basic-аутентификации (REQ-01).
- Данные пользователя: топология с именем, выбранным для прогона (в плане — `demo-e2e`), в ответе `GET …/topologies` отсутствует до этапа 1 (REQ-02). Файл, который будет создан на этапе 5, в HDFS отсутствует. Фикстура принадлежит этому journey и никем больше не создаётся.
- Устройство / сеть: HTTP-клиент с поддержкой TLS обращается к `https://<хост>:8443`; шлюз Knox запущен, административный API `…/gateway/admin/api/v1/topologies` доступен, за шлюзом работает сервис WebHDFS с каталогом `/tmp`. Конкретный хост и режим проверки сертификата требованиями не заданы — см. пробел 5.

## Основной путь

Администратор обращается к шлюзу с учётными данными `admin` / `admin-password` и запрашивает `GET …/admin/api/v1/topologies`, убеждаясь, что записи с именем `demo-e2e` в списке нет. Он отправляет `PUT …/admin/api/v1/topologies/demo-e2e` с XML-описанием топологии (провайдер ShiroProvider, сервис WEBHDFS) и получает HTTP 200. Далее он опрашивает `GET …/topologies`, пока запись `demo-e2e` с полями `name` и `timestamp` не появится в списке — это должно произойти не позднее чем через 30 секунд. Убедившись, что топология применена, администратор обращается к её gateway-URL: `GET …/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS` возвращает HTTP 200 и JSON с полем `FileStatuses`. Он записывает файл `PUT …/gateway/demo-e2e/webhdfs/v1/tmp/demo-e2e.txt?op=CREATE&overwrite=true` с содержимым в теле и получает HTTP 201 с заголовком `Location`, содержащим путь файла. Тем же gateway-URL он читает файл обратно — `GET …?op=OPEN` возвращает HTTP 200 и тело, байт в байт совпадающее с записанным. Завершая сеанс, администратор отправляет `DELETE …/admin/api/v1/topologies/demo-e2e`, получает HTTP 200 и подтверждает демонтаж двумя наблюдениями: записи `demo-e2e` в `GET …/topologies` больше нет, а повторный `GET …/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS` с верными учётными данными возвращает HTTP 404. Становится кейсом `TC-J01-00`.

## Зависимости и риски

- Порядок этапов жёсткий и не переставляется: gateway-URL начинает обслуживать запросы только после того, как топология появилась в реестре (2 → 3 → 4), чтение файла требует его предварительной записи (5 → 6), проверка отсутствия — предварительного удаления (7 → 8).
- Тайминг. REQ-02 задаёт окно «не позднее чем через 30 секунд», а не мгновенное применение: этап 3 обязан быть опросом с ретраями внутри этого окна, а не однократным запросом. Наблюдаемое поведение внутри окна требованиями не задано — см. пробел 4.
- Внешние системы: демонстрационный LDAP шлюза (REQ-01) и кластер HDFS за сервисом WebHDFS (REQ-03…REQ-05). Их недоступность ломает этапы 1 и 4–6, но реакция шлюза на неё в корпусе не описана, поэтому в план не заведена ни этапом, ни вариантом.
- Стенд. Хост во всех требованиях — плейсхолдер `<хост>`, путь в REQ-04/REQ-05 — плейсхолдер `<путь к файлу>`; выбранные планом `demo-e2e` и `/tmp/demo-e2e.txt` являются решением теста, а не корпуса. Требования также не говорят, доверенный ли TLS-сертификат у порта 8443 — см. пробел 5.
- Повторяемость прогона. Этап 8 возвращает в исходное состояние реестр топологий, но не HDFS: файл `/tmp/demo-e2e.txt` остаётся, а операции его удаления в корпусе нет. Второй прогон поэтому стартует не с чистого состояния этапа 5 и попадает ровно в неопределённость пробела 3.
- Изоляция journey. Все фикстуры journey создаёт сам (этапы 1, 2, 5); ни один этап не потребляет данные, созданные вне него.

## Выявленные пробелы

- **Пробел 1.** Не определено, что происходит при попытке администрировать топологии не-административной учётной записью. REQ-02: «Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>` **от `admin`** … возвращает HTTP 200»; REQ-06: «Запрос `DELETE …/admin/api/v1/topologies/<имя>` **от `admin`** возвращает HTTP 200»; REQ-01: «Запрос с верными учётными данными передаётся сервису; код ответа определяется операцией (REQ-02…REQ-06)». Учётная запись `guest` в LDAP объявлена и её пароль верен, но код ответа шлюза на её `PUT`/`DELETE` не назван ни одним требованием. Вариант на разграничение прав поэтому не создан.
- **Пробел 2.** Отказ аутентификации описан только по одной причине. REQ-01: «Запрос с **неверным паролем** возвращает HTTP 401, тело ответа содержит текст `Authentication failed`». Для несуществующего в LDAP логина, для пустого значения заголовка `Authorization` и для запроса вовсе без этого заголовка код и тело ответа не заданы, хотя REQ-01 открывается словами «**Любой** запрос через шлюз требует Basic-аутентификации».
- **Пробел 3.** Противоречие между параметром и описанным эффектом в REQ-04: запрос назван как `PUT …?op=CREATE&**overwrite=true**`, а результат описан только для отсутствующего файла — «с содержимым в теле **создаёт файл**: HTTP 201, заголовок `Location` содержит путь файла». Что возвращает тот же запрос на уже существующий путь и заменяется ли содержимое — не сказано. REQ-05 усиливает неопределённость: «содержимое, байт в байт совпадающее с загруженным **в REQ-04**» не разрешает, о какой из двух загрузок идёт речь.
- **Пробел 4.** Поведение gateway-URL вне «установившегося» состояния не задано. REQ-02: «Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies` …, а её gateway-URL **начинает обрабатывать** запросы REQ-03…REQ-05. Перед деплоем топологии с этим именем в списке `GET …/topologies` нет». Требование говорит про список до деплоя, но не про gateway-URL до деплоя и не про gateway-URL внутри 30-секундного окна — притом что для симметричной ситуации после удаления REQ-06 наблюдаемое называет явно: «запрос REQ-03 к ней с верными учётными данными возвращает HTTP 404».
- **Пробел 5.** Стенд не специфицирован до уровня, на котором кейс запускается. Хост во всех требованиях — `<хост>` (REQ-02: «`PUT https://<хост>:8443/…`»), путь файла — `<путь к файлу>` (REQ-04, REQ-05), имя топологии — `<имя>` (REQ-02, REQ-06). Не сказано также, существует ли каталог `/tmp` в HDFS до прогона, хотя REQ-03 требует от него ответа с полем `FileStatuses`, и является ли TLS-сертификат шлюза на порту 8443 доверенным или самоподписанным.

## Уточняющие вопросы

1. Какой HTTP-код и какое тело возвращает шлюз, когда `guest` / `guest-password` выполняет `PUT` или `DELETE …/admin/api/v1/topologies/<имя>`? — блокирует этапы 2 и 7 (граница «от `admin`») и вариант на разграничение прав, который без ответа не заведён.
2. Какой код и какое тело возвращает шлюз для логина, отсутствующего в LDAP, и для запроса без заголовка `Authorization` — те же HTTP 401 и `Authentication failed`, что и для неверного пароля? — блокирует вариант TC-J01-01.
3. Что возвращает повторный `PUT …/webhdfs/v1/<путь>?op=CREATE&overwrite=true` на уже существующий путь — снова HTTP 201 с заголовком `Location`, и заменяется ли содержимое файла новым? — блокирует вариант TC-J01-03 и повторный прогон journey (см. пробел 3).
4. Что возвращает `GET …/gateway/<имя>/webhdfs/v1/tmp?op=LISTSTATUS` до деплоя топологии и в течение 30-секундного окна после HTTP 200 на `PUT`? Считается ли ответ внутри окна допустимым промежуточным состоянием, а не дефектом? — блокирует этапы 3 и 4.
5. Какие конкретные `<хост>:8443`, `<имя>` топологии и `<путь к файлу>` использовать на демо-стенде, гарантируется ли существование каталога `/tmp` в HDFS до прогона, и требуется ли отключать проверку TLS-сертификата шлюза? — блокирует этапы 1, 4, 5 и 6.
6. Должен ли journey удалять созданный файл `/tmp/demo-e2e.txt` в постусловии? REQ-06 возвращает в исходное состояние только реестр топологий, операции удаления файла в корпусе нет, поэтому повторный прогон начинается с уже существующим файлом. — блокирует постусловие этапа 8 и повторяемость `TC-J01-00`.
