# E2E Journey / Suite Plan

## Общая информация

- **ID journey:** J01-knox-topology-webhdfs
- **Название:** Шлюз Knox: развернуть топологию, записать и прочитать файл в HDFS через шлюз, снять топологию
- **Цель journey:** Подтвердить, что администратор может развернуть топологию через админский API шлюза, работать через её gateway-URL с WebHDFS (листинг, запись, чтение) под Basic-аутентификацией LDAP и снять топологию так, что её URL перестаёт обслуживать запросы
- **Приоритет:** Критический
- **Функциональные области:** аутентификация, администрирование топологий, проксирование WebHDFS, жизненный цикл топологии
- **Покрываемые требования:** REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06

## Индекс требований

| Анкор | Формулировка требования | Источник (файл, раздел) |
|---|---|---|
| REQ-01 | Любой запрос через шлюз требует Basic-аутентификации против LDAP. В демонстрационном LDAP две учётные записи: `admin` / `admin-password` и `guest` / `guest-password`. Запрос с неверным паролем возвращает HTTP 401, тело ответа содержит текст `Authentication failed`. Запрос с верными учётными данными передаётся сервису; код ответа определяется операцией (REQ-02…REQ-06) | knox-demo.md § Аутентификация |
| REQ-02 | Запрос `PUT https://<хост>:8443/gateway/admin/api/v1/topologies/<имя>` от `admin` с XML-описанием топологии (провайдер ShiroProvider, сервис WEBHDFS) возвращает HTTP 200. Не позднее чем через 30 секунд топология присутствует в ответе `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и `timestamp`), а её gateway-URL начинает обрабатывать запросы REQ-03…REQ-05. Перед деплоем топологии с этим именем в списке `GET …/topologies` нет | knox-demo.md § Администрирование топологий |
| REQ-03 | Запрос `GET https://<хост>:8443/gateway/<имя>/webhdfs/v1/tmp?op=LISTSTATUS` от аутентифицированного пользователя возвращает HTTP 200 и JSON с полем `FileStatuses` | knox-demo.md § Проксирование WebHDFS |
| REQ-04 | Запрос `PUT …/webhdfs/v1/<путь к файлу>?op=CREATE&overwrite=true` с содержимым в теле создаёт файл: HTTP 201, заголовок `Location` содержит путь файла | knox-demo.md § Проксирование WebHDFS |
| REQ-05 | Запрос `GET …/webhdfs/v1/<путь к файлу>?op=OPEN` возвращает HTTP 200 и содержимое, байт в байт совпадающее с загруженным в REQ-04 | knox-demo.md § Проксирование WebHDFS |
| REQ-06 | Запрос `DELETE …/admin/api/v1/topologies/<имя>` от `admin` возвращает HTTP 200. После удаления топология отсутствует в списке `GET …/topologies`, а запрос REQ-03 к ней с верными учётными данными возвращает HTTP 404 | knox-demo.md § Жизненный цикл топологии |

## Начальное состояние

- Аккаунт: демонстрационный LDAP шлюза содержит две учётные записи — `admin` / `admin-password`
  и `guest` / `guest-password` (REQ-01). Обе используются в journey: `admin` — для всех этапов
  основного пути, `guest` — в варианте TC-J01-03.
- Авторизация: клиент не хранит сессию; каждый запрос несёт собственный заголовок Basic-авторизации
  (REQ-01). Отдельного шага входа в journey нет — аутентификация проверяется на каждом запросе.
- Данные пользователя: топология с именем прогона (далее `demo-e2e`) на шлюзе не развёрнута и
  отсутствует в ответе `GET …/topologies` — это предусловие задано самим REQ-02. Файл
  `/tmp/demo-e2e.txt` в HDFS не создан. Каталог `/tmp` в HDFS существует и доступен на чтение и
  запись — без этого этапы 4–6 неисполнимы (см. вопрос 1).
- Устройство / сеть: шлюз Knox запущен и слушает HTTPS на порту 8443, сервис WEBHDFS за шлюзом
  доступен. Адрес `<хост>` требованиями не задан (пробел 8, вопрос 1) — его подставляет прогон.
  Сертификат шлюза самоподписанный, поэтому клиент должен быть настроен на его приём; требованиями
  это не описано и в наблюдаемые не входит.

## Проверяемые состояния

| Измерение состояния | Что должно наблюдаться | REQ |
|---|---|---|
| Аутентификация запроса | верные учётные данные — запрос передан сервису и код определяется операцией; неверный пароль — HTTP 401 и текст `Authentication failed` в теле, на любом эндпоинте шлюза | REQ-01 |
| Реестр топологий | переход «записи `name` = `demo-e2e` нет → запись с полями `name` и `timestamp` есть → записи нет» в ответе `GET …/topologies` | REQ-02, REQ-06 |
| Доступность gateway-URL топологии | переход «URL не обслуживает → обслуживает REQ-03…REQ-05 → отвечает HTTP 404 на тот же запрос с верными учётными данными» | REQ-02, REQ-03, REQ-06 |
| Окно развёртывания | запись топологии появляется в списке не позднее чем через 30 секунд после HTTP 200 на PUT | REQ-02 |

| Целостность содержимого | тело ответа `op=OPEN` байт в байт равно телу запроса `op=CREATE` | REQ-05 |

## Основной путь

Администратор с учётными данными `admin` / `admin-password` запрашивает список топологий шлюза и
убеждается, что топологии `demo-e2e` в нём нет. Он разворачивает её запросом `PUT` в админский API
с XML-описанием (провайдер ShiroProvider, сервис WEBHDFS), получает HTTP 200 и в течение 30 секунд
видит запись `demo-e2e` с полями `name` и `timestamp` в ответе `GET …/topologies`. Через
gateway-URL новой топологии он выполняет листинг каталога `/tmp` в HDFS и получает HTTP 200 с полем
`FileStatuses`, затем записывает файл `/tmp/demo-e2e.txt` запросом `op=CREATE&overwrite=true` и
получает HTTP 201 с заголовком `Location`, содержащим путь файла. Он читает файл обратно запросом
`op=OPEN` и сравнивает тело ответа с загруженным содержимым байт в байт. Завершая сценарий, он
удаляет топологию запросом `DELETE` в админский API, получает HTTP 200 и убеждается, что записи
`demo-e2e` в списке топологий больше нет, а тот же запрос листинга `/tmp` через её gateway-URL с
верными учётными данными возвращает HTTP 404. Кейс: `TC-J01-00`.

| ID | Ветвление от этапа | Отклонение | Зачем проверяем | REQ |
|---|---|---|---|---|
| TC-J01-01 | Этап 2 | `PUT …/admin/api/v1/topologies/demo-e2e` отправляется с логином `admin` и неверным паролем | Шлюз обязан отсекать неаутентифицированный запрос до админского API: ожидается HTTP 401 и текст `Authentication failed` в теле, а запрос не передаётся сервису — записи `demo-e2e` в `GET …/topologies` не появляется | REQ-01, REQ-02 |
| TC-J01-02 | Этап 4 | `GET …/gateway/demo-e2e/webhdfs/v1/tmp?op=LISTSTATUS` отправляется с неверным паролем при уже развёрнутой топологии | Правило «любой запрос через шлюз» проверяется и на data-path, не только на админском API: ожидается HTTP 401 и текст `Authentication failed`; топология при этом остаётся в списке `GET …/topologies` | REQ-01, REQ-03 |
| TC-J01-03 | Этап 4 | Тот же листинг выполняется от второй учётной записи LDAP — `guest` / `guest-password` | REQ-03 разрешает операцию любому аутентифицированному пользователю, в отличие от REQ-02 и REQ-06, где явно указан `admin`: ожидается HTTP 200 и JSON с полем `FileStatuses` | REQ-01, REQ-03 |

## Зависимости и риски

- Этапы 4–6 исполнимы только после этапа 3: до появления топологии в списке gateway-URL по REQ-02
  ещё не обязан обслуживать запросы. Порядок этапов менять нельзя.
- Этап 3 содержит временное окно: проверка «не позднее 30 секунд» требует засечь момент ответа
  HTTP 200 на этапе 2 и опрашивать `GET …/topologies` до истечения окна. Слишком ранняя
  единственная проверка даст ложное падение, слишком поздняя — не проверит границу.
- Этап 6 проверяет данные, созданные на этапе 5, а этап 8 — данные этапов 2 и 4: journey нельзя
  разрезать между ними, вторая часть унаследовала бы состояние первой. Единственная граница
  достигнутой цели внутри корпуса — «файл записан и прочитан», но снятие топологии (REQ-06) без
  предшествующего деплоя (REQ-02) непроверяемо, поэтому деплой / использование / снятие остаются
  одним journey из 8 этапов — это потолок, а не превышение.
- Внешние системы: демонстрационный LDAP шлюза (REQ-01) и сервис WEBHDFS за шлюзом (REQ-03…REQ-05).
  Недоступность любого из них делает journey неисполнимым, а не проваленным.
- Journey изменяет состояние стенда: создаёт файл в HDFS и топологию на шлюзе. Повторный прогон
  требует, чтобы предусловие REQ-02 («перед деплоем топологии с этим именем в списке нет») снова
  выполнялось; какое состояние остаётся после этапа 8, требованиями определено только для реестра
  топологий, но не для файла в HDFS (пробел 7, вопрос 7).
- Все запросы идут по HTTPS на порт 8443 с самоподписанным сертификатом стенда; настройка доверия
  сертификату — техническая предпосылка прогона, требованиями не описанная и в наблюдаемые не
  входящая.

## Выявленные пробелы

- **Пробел 1.** REQ-02 описывает ответ `GET …/topologies` только по содержимому — «топология
  присутствует в ответе `GET …/topologies` (JSON-список, каждая запись содержит поля `name` и
  `timestamp`)» — и не называет HTTP-код этого запроса. REQ-01 отсылает за кодом к операции:
  «код ответа определяется операцией (REQ-02…REQ-06)», но для листинга топологий кода нигде нет.
  Этапы 1, 3 и 8 наблюдают этот ответ.
- **Пробел 2.** REQ-02 формулирует «Перед деплоем топологии с этим именем в списке
  `GET …/topologies` нет» как предусловие и ничего не говорит о реакции на его нарушение: что
  вернёт `PUT …/topologies/demo-e2e`, если топология с этим именем уже развёрнута — 200 с
  перезаписью, ошибку или иной код, — не определено.
- **Пробел 3.** REQ-02 и REQ-06 явно требуют учётную запись `admin` («от `admin`»), а REQ-01
  описывает LDAP с двумя записями и говорит только про неверный пароль. Реакция на админские
  запросы от `guest` с верным паролем не определена: 401, 403 или выполнение. Из-за этого вариант
  TC-J01-03 ограничен операцией REQ-03, где формулировка «от аутентифицированного пользователя»
  однозначна.
- **Пробел 4.** REQ-01 определяет только случай неверного пароля: «Запрос с неверным паролем
  возвращает HTTP 401, тело ответа содержит текст `Authentication failed`». Что возвращает шлюз на
  запрос вовсе без заголовка `Authorization` и на запрос от несуществующего в LDAP пользователя —
  не определено, хотя первая фраза требования звучит шире: «Любой запрос через шлюз требует
  Basic-аутентификации против LDAP».
- **Пробел 5.** Реакция на обращение к несуществующим ресурсам не определена: REQ-05 описывает
  `op=OPEN` только для файла, загруженного в REQ-04, а REQ-06 — только удаление существующей
  топологии. Что вернут `op=OPEN` по несуществующему пути и `DELETE …/topologies/<имя>` для
  неразвёрнутой топологии, корпус не говорит.
- **Пробел 6.** REQ-04 содержит параметр `overwrite=true`, но описывает только создание файла:
  «с содержимым в теле создаёт файл: HTTP 201». Результат повторной записи по тому же пути с новым
  содержимым не описан, а REQ-05 привязывает эталон сравнения к «загруженному в REQ-04», из-за чего
  для второй записи эталон неоднозначен. Варианта на перезапись в этом плане нет именно поэтому.
- **Пробел 7.** REQ-06 описывает последствия удаления топологии только для реестра и gateway-URL:
  «топология отсутствует в списке `GET …/topologies`, а запрос REQ-03 к ней с верными учётными
  данными возвращает HTTP 404». Судьба файла `/tmp/demo-e2e.txt`, записанного через эту топологию
  на этапе 5, не определена — это постусловия основного кейса и повторяемость прогона.
- **Пробел 8.** Все адреса в корпусе даны как шаблон: `https://<хост>:8443/…`. Конкретный адрес
  стенда, а также доступный на запись путь HDFS (в REQ-03 упомянут только каталог `/tmp` в примере
  листинга) требованиями не заданы, поэтому конкретные тестовые данные этапов 1–8 без ответа
  человека не формируются.

## Уточняющие вопросы

1. Какой адрес стенда подставлять вместо `<хост>` в `https://<хост>:8443/…` и какой путь HDFS
   доступен на запись для файла прогона (подтверждается ли `/tmp` из примера REQ-03)? Блокирует
   этапы 1–8 и все кейсы journey: без этого тестовые данные остаются шаблоном.
2. Какой HTTP-код возвращает `GET …/admin/api/v1/topologies` при верных учётных данных `admin`?
   Блокирует этапы 1, 3 и 8 — в каждом из них это наблюдаемый результат.
3. Что возвращает `PUT …/admin/api/v1/topologies/<имя>`, если топология с этим именем уже
   развёрнута? Блокирует этап 2: от ответа зависит, обязан ли прогон гарантированно снимать
   топологию перед стартом или может опираться на перезапись, и появляется ли отдельный вариант на
   повторный деплой.
4. Что возвращает админский API (`PUT` и `DELETE …/topologies/<имя>`) на запрос от `guest` с верным
   паролем — 401, 403 или выполнение операции? Блокирует расширение варианта TC-J01-03 на админские
   операции; сейчас вариант ограничен REQ-03.
5. Что возвращает шлюз на запрос без заголовка `Authorization` и на запрос от отсутствующего в LDAP
   пользователя — тот же HTTP 401 с текстом `Authentication failed` или иной ответ? Блокирует
   добавление варианта на эти две ветки к TC-J01-01 и TC-J01-02.
6. Что возвращают `GET …?op=OPEN` для несуществующего файла и `DELETE …/topologies/<имя>` для
   неразвёрнутой топологии? Блокирует добавление вариантов на этапы 6 и 7.
7. Остаётся ли файл `/tmp/demo-e2e.txt` в HDFS после удаления топологии, через которую он был
