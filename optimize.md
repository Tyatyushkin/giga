## Принцип

Стоимостная иерархия проекта:

| Уровень | Порядок стоимости одного действия |
|---|---|
| Python-скрипт | миллисекунды |
| Один вызов агента | минуты, тысячи выходных токенов |
| Одна волна (P агентов + барьер) | минуты по самому медленному |
| Полный прогон | до 3 итераций × волны |

Отсюда два правила, которым подчинён весь план:

1. **Проверка, сдвинутая на уровень влево, экономит 3–4 порядка.** Всё механическое — в скрипт.
2. **Время LLM определяют выходные токены, а не входные.** Они генерируются последовательно.
   Ускорять надо печать: сокращать её объём и распараллеливать.

Дополнительный фактор среды: DeepSeek/Qwen хуже frontier-моделей держат длинные промпты с
плотностью запретов и чаще ошибаются на вложенном JSON. Это смещает приоритет в сторону
«гарантия в коде, а не в тексте промпта».

### O-13. Фаза изучения у аналитика — самое дешёвое ускорение в плане

- [ ] Предписать **одно пакетное чтение**: `read_many_files` одним вызовом на все входные файлы
- [ ] Запретить повторные обращения к исходникам — работать с прочитанным
- [ ] Поднять `max_turns` аналитика с 25 до 40
- [ ] Убрать `zvuk-sample.md` из дефолтного glob (дубль T-07 из таск-листа дефектов)
- [ ] Кэшировать `_reqindex.json` по хешу входа — пропускать шаг 0 на повторных прогонах

**«Изучение» — это три разные вещи, и только одна неустранима:**

| Что | Устранимо |
|---|---|
| Чтение файлов | ✅ сокращается до одного обращения |
| Разбор прозы — найти, где в тексте требования | ✅ выносится в скрипт (O-03) |
| Группировка в journey | ❌ **это и есть работа модели** |

**Главная причина — число обращений, а не объём.** Модели по умолчанию читают файлы по одному.
Каждое чтение — полный round trip: префилл всего накопленного контекста → генерация вызова →
результат → контекст вырос. Аналитику нужно 6 файлов (три требования, `docs/format.md`,
`GIGACODE.md`, `templates/suite-plan.md`), плюс перечитывания по ходу рассуждения.

```
последовательно:  K обращений × растущий контекст  ≈  K × C/2 работы префилла
одним пакетом:    1 обращение × C
```

При K=8 и контексте до ~25 К токенов это порядка 100 К токенов префилла против 25 К — **вчетверо
больше работы** на том же материале, и вся она тратится до того, как модель начала думать.

**Ключевой факт:** `read_many_files` **уже есть** в инструментах аналитика
(`requirements-analyst.md:6`), но спека нигде не велит его использовать — строка 33 говорит
просто «Read every requirement file», и способ выбирает модель. Правка — одна строка текста.

**Побочный эффект `max_turns: 25`.** Если 8 ходов сгорели на чтение, на индексацию, группировку
и написание N планов остаётся 17. У аналитика самый маленький бюджет ходов при самой большой
задаче (у дизайнера и писателей тестов — 40, у критика — 30).

**Чего делать не стоит: не срезать корпус для аналитика.** §3 «Бизнес-требования» — это 63 %
`zvuk.md`, и соблазн отдать только его обманчив: §1 описывает пользовательский путь, то есть
прямой материал для группировки в journey; §6 и §7 питают разделы «Зависимости и риски» и
«Выявленные пробелы». Урезав, ускорим чтение и испортим главное, ради чего аналитик существует.
Аналитик — единственный агент, которому весь корпус нужен законно; срез уместен для дизайнера
(O-09), и то с оговоркой про критика.

### O-03. `scripts/extract_reqs.py` — индекс требований скриптом

- [ ] Написать экстрактор двух форматов: `- **REQ-01.** текст` и `| **BR-001** | … |`
- [ ] Выход: `output/suites/_reqindex.json` — `id`, дословный `text`, `source` (`файл § раздел`)
- [ ] Режим `--markdown --only REQ-01,REQ-04` — готовый блок «Индекс требований» для вставки в план
- [ ] Режим `--prefix BR,REQ` — корпус нумерует не только требования
- [ ] `requirements-analyst.md` Step 0 и Step 2: вызывать скрипт, не печатать текст руками
- [ ] `templates/suite-plan.md`: заголовок таблицы без «(кратко)» — формулировки дословные

**Зачем — две разные экономии, и вторая крупнее.**

*Экономия печати.* Сейчас текст требований перепечатывается моделью до четырёх раз: в `reqIndex`
внутри `_index.json` и по разу в раздел «Индекс требований» каждого плана. Это чистая
транскрипция — работа, где модель ничего не решает, но платит полной ценой последовательной
генерации.

*Экономия изучения.* Аналитик перестаёт **искать** требования в 23 КБ смешанной прозы и получает
готовую структуру: `id`, дословный текст, раздел-источник. Шаг 0 «построй внутренний индекс
атомарных утверждений» исчезает как задача модели целиком. См. O-13 — это половина того, что
делает фазу изучения долгой.

**Ключевой факт:** `reqIndex` в `_index.json` **не читает ни один потребитель** — проверено по
`build_gate_questions.py`. Заменить на `reqIndexFile` + `reqPrefixes`.

Дублирование индекса внутри планов — намеренное (`requirements-analyst.md:53-56`): параллельные
дизайнеры не видят друг друга, план обязан быть самодостаточным. Но самодостаточность не требует,
чтобы текст печатала модель. Скрипт подставит те же строки.

**Прототип этого скрипта был написан и откачен** в этой же ветке — оба формата корпуса
разбирались корректно, 40 записей (BR-16, BG-3, AS-3, RS-4, REQ-14). Восстановить из истории
обсуждения.

**Проверка:** `--only` с тремя анкорами отдаёт валидную markdown-таблицу; `--prefix BR` отдаёт 16.

пополняется батч.

```
T_волны = max(дизайнеры) + max(критики)      ← сейчас
T_конв  = max_j(дизайнер_j + критик_j)       ← возможное
```

Journey, отработавший за 3 минуты, ждёт того, кто идёт 8. Умножить на 3 итерации.

**Барьер здесь не нужен ни для чего.** Он оправдан, когда следующей стадии нужны результаты
всех предыдущих. Journey изолированы по построению — «один пишущий на путь», критик не читает
чужие кейсы. Собственное свойство корректности проекта и делает барьер бессмысленным.

### O-07. Декомпозиция аналитика по стадиям

- [ ] Фаза 1a — обнаружение journey: 1 агент, весь корпус, выход `output/suites/_skeleton.json`

- [ ] Фаза 1c — сборка `_index.json`: скрипт, не агент

- [ ] Температура писателя плана 0.1 — он не решает, а разворачивает готовую группировку

**Что глобально, а что нет:**

| Шаг | Нужен глобальный взгляд | Куда |
|---|---|---|
| Индексация `REQ-XX` | ❌ механика | скрипт (O-03) |
| Поиск journey | ✅ **да** | 1 агент, выход маленький |

| Сборка `_index.json` | ❌ агрегация | скрипт |

**Ловушка, которую нельзя допустить:** не резать корпус между N аналитиками. Journey находится
только взглядом на всё сразу; аналитик на куске требований выдаст группировку по фичам вместо
сквозных путей — ровно тот провал, против которого построен проект. Декомпозиция **по стадиям,
а не по входу.**

новый документ. Для шага, который нельзя пропускать, это ровно неверное впечатление. Скрипт
срезает frontmatter и сдвигает заголовки на `--level`. Отсутствующий скилл печатает в промпт
«ОШИБКА ВКЛЮЧЕНИЯ» и выходит с кодом 2 — молчаливо пустой вставки не бывает.

1. `GIGACODE.md` предписывал писателям **дописывать общий** `output/tests/README.md`. Это путь

### O-12. MCP-сервер поверх скриптов

- [ ] Обернуть детерминированное ядро, когда скриптов станет 5–6

```
validate_cases(path, journey?)     → {counts, findings[], blockers}
build_gate_questions(index, flags) → {gateQuestions[], lists{}, defaults{}}
gate_check(questions, answers)     → {passed, nextAction, parallel, unit}
extract_reqs(sources, prefix?)     → {reqIndex[], duplicateIds[]}
check_state(path)                  → {valid, problems[]}
```

Выигрыш не в скорости, а в **портируемости**: любой MCP-клиент получает детерминированные шлюзы
без клонирования репозитория и без Python в окружении.

**Чего в MCP не делать:** полную цепочку одним вызовом. Результат вызова уходит вызывающей
модели, и она решает, показывать ли его человеку — это ровно тот провал, против которого написан
протокол вопросов. Плюс серверу пришлось бы стать агентным рантаймом с собственным доступом к
модели.

**Отложено:** машина состояний в MCP (`e2e_next()` возвращает следующий шаг или `ask_human` и не
продвигается, пока контракт не выполнен). Идея хорошая — `gate_check.py` с его `nextAction` уже
первый её узел — но процедура за последние дни менялась трижды, фиксировать её в коде рано.
Плата: порядок фаз перестанет правиться редактированием markdown.

### Семантический поиск для ускорения цикла

**Нет.** Три причины:

1. **Не тот axis.** Семантика сокращает вход, а узкое место — выход. Вход (48 КБ) и так
   помещается в контекст.
2. **Ломает главную операцию.** Работа критика — доказательство отсутствия («не определяет ни
   одно требование»). Top-K по близости принципиально не умеет доказывать отсутствие; промах
   ретривера даёт ложный BLOCKER, то есть лишнюю полную итерацию.
3. **Есть точная адресация.** Требования пронумерованы, journey заявляет свои анкоры. Выборка по
   id даёт точность и полноту 1.0 при нуле зависимостей. Семантика была бы нечёткой версией того,
   что делается точно.

**Где уместна** (нечёткий подбор кандидатов, не проверка полноты):

- дедупликация вопросов и пробелов между journey — Фаза 3, сейчас это делает модель
- поиск противоречий в требованиях — кандидаты для суждения модели
- обнаружение пересечений между journey и между вариантами кейсов

Во всех трёх выход — список кандидатов, а не вердикт. Отдельная утилита, не часть цикла.

**Когда пересмотреть:** если придут требования без нумерации — адресовать будет нечем, и тогда
семантика незаменима.
