### O-14. Убрать дублирование md+json — сделано

`qa-designer` писал `.md` и `.json` на каждый кейс — содержательно то же самое, полной ценой
выходных токенов дважды. Проверено: ни один потребитель (агенты, скрипты) не читает
`steps[].requirements` — единственное поле JSON, не выводимое из Markdown механически
(таблица «Шаги» не несёт колонки с REQ-якорем на уровне шага, только кейс целиком).

Написан `scripts/build_case_json.py` — детерминированный конвертер `.md → .json`, переиспользует
парсер `validate_cases.py` (`split_sections`, `parse_table`, `parse_fields`). Прогнан на эталонном
кейсе `examples/J01-onboarding-first-play/TC-J01-00.md`: результат совпал с существующим `.json`
по всем полям кроме `clarifyingQuestions`/`gaps` — и там разница показательна: старый ручной JSON
оказался не копией, а **пересказом** того же текста более короткими фразами. Конвертер убирает
не только двойную стоимость печати, но и риск смыслового расхождения между форматами, который
ручное дублирование создавало по конструкции.

`qa-designer.md` переписан: дизайнер пишет только `.md`; самопроверка теперь
`build_case_json.py` → `validate_cases.py`, в этом порядке. `docs/format.md`, `GIGACODE.md`
(таблица владения путями) и подсказки линтера при рассинхроне обновлены. `validate_cases.py`
регрессии не показал — эталонный кейс по-прежнему 0/0/0.

**Ожидаемый эффект:** совпадает с оценкой в `tasks.rtf` — JSON эталонного кейса длиннее
Markdown-версии (262 строки против 77), то есть исключение ручной печати JSON снимает
существенную долю выходных токенов дизайнера за кейс. Дизайнер — самая дорогая по печати
стадия конвейера (`result.md` §3.1: 44–110 тыс. токенов на journey), так что эффект приходится
ровно на узкое место, найденное измерениями.

### O-11 (частично). Протокол вопроса — общий include

Полное дублирование правил `run.md` (355→254 строк, уже частично сделано раньше) и `analyze.md`
не byte-identical — но механика «как правильно вызвать инструмент вопроса, что делать при отказе,
что запрещено» повторялась в обоих текстом, а не ссылкой. Вынесено в `docs/question-protocol.md`
(общая механика, без привязки к конкретной фазе); `run.md` и `analyze.md` подключают его через
`!{cat docs/question-protocol.md}` — механизм уже использовался в проекте (`run.md` листинг
файлов), нового ничего не введено.

**При слиянии заменено.** Ту же границу «общее ↔ специфичное для команды» независимо провела
ветка `skills`, но включает протокол через `scripts/include_skill.py <имя> --level N`, а не
`!{cat}`: `cat` вставляет заголовок H1 внутрь `### Фазы 1.5`, и фаза начинает читаться как
законченная — из-за этого и появился `--level`, понижающий ранг заголовков по месту вставки.
`docs/question-protocol.md` (23 строки) целиком содержится в `.gigacode/skills/human-gate.md`
(100 строк: режимы A/B, лимиты полей, запись ответа, режим `--no-ask`), поэтому файл удалён,
а оба вызова переведены на `include_skill.py`. Два источника одного протокола — ровно то,
что этот пункт и устранял. Команда-специфичное («какие фазы гейтуют», «что отключает
вопросы») осталось в месте вызова — вынос сделан по границе «общее ↔ специфичное для команды»,
а не «всё в одну кучу».

**Не тронуто:** тройная запись контракта Фазы 2.5 (`GIGACODE.md` + `run.md` + `pytest-stub-writer.md`)
— крупная правка с риском рассинхрона на трёх файлах, отдельная задача. `design.md`/`review.md`
дублирования почти не содержат (одна строка-указатель на инструмент вопроса) — включать их не
имело смысла.

### O-16 (R4). Дробить генерацию крупного кейса на подпроцессы — оценено и отклонено

Исходная идея: главный кейс на 20–24 шага печатается дизайнером одним блоком (~150 строк
md+json); разбить печать на части (по этапам/по 5–6 шагов за вызов) снизит риск обрыва и объём
единичного вывода.

**Почему не делаю:**

1. **O-14 уже снимает половину проблемы, на которой построен R4.** ~150 строк вывода на кейс — это
   счёт «md + json»; после O-14 дизайнер печатает только md, то есть ровно ~77 строк на эталонном
   кейсе вместо 262+77. Мотивация R4 («блок слишком велик») ослаблена вдвое тем же изменением,
   которое уже сделано, без единой новой строки кода под R4.
2. **Риск бьёт по главному инварианту проекта.** «Непрерывность состояния» (`GIGACODE.md`, правило 5)
   и цепочный проход критика (`test-critic.md`, «Chain pass») требуют, чтобы значения, созданные на
   раннем шаге, дословно повторялись на позднем — это внутрикейсовая связность, которую пишет один
   контекст за один проход. Разбить печать одного кейса между несколькими вызовами агента означает
   либо (а) передавать полное состояние кейса между вызовами вручную — дополнительная печать,
   съедающая часть выигрыша, либо (б) полагаться на память между вызовами, которой между агентами
   в этом проекте по конструкции нет (`GIGACODE.md`: «агенты в одной волне… не делят контекст»).
3. **Этот проект уже дважды наказан за оптимизацию без замера.** O-06 и O-08 (`result.md` §7.4,
   `optimize.md` строки выше) — оба спроектированы на правдоподобном расчёте и оба на живом прогоне
   дали от нуля до заявленного эффекта, по причинам, которые расчёт не мог предвидеть (выровненная
   декомпозиция journey). Резать генерацию кейса на части — структурная правка того же калибра, но
   без единого прогона, подтверждающего, что дробление не приведёт к рассинхрону состояния между
   частями. Правильный следующий шаг, если объём после O-14 всё ещё окажется проблемой — измерить
   заново на актуальном (после O-14) объёме, не проектировать по старой цифре.

### O-18. Линтер ловит выдуманные REQ-id и битые ссылки «Вариант от» — сделано 19.08.2026

Найдено при разборе устойчивости пайплайна к более слабой модели (не из `tasks.rtf` — отдельный
запрос). Два класса ошибок, которые слабая модель делает заметно чаще сильной, были раньше видны
только критику (семантическое чтение) или не видны вообще:

1. **Выдуманный/опечатанный REQ-id** в поле «Покрываемые требования» — критик мог это заметить
   только если специально сверял каждый id с индексом; линтер этого не делал вовсе.
2. **«Вариант от» ссылается на несуществующий файл** — раньше проверялся только формат поля
   (`—` vs что-то), не факт существования цели.

Оба добавлены в `validate_cases.py`: `req-id-unknown` (BLOCKER, сверяет с `reqIndex` из
`_index.json`) и `variant-target-missing` (BLOCKER, проверяет наличие файла в каталоге).

**Путь к индексу выводится от `target`, не зашит в cwd.** Первая версия брала фиксированный
`output/suites/_index.json` по умолчанию — и тут же дала ложный BLOCKER на эталонном примере
`examples/J01-onboarding-first-play`, потому что в репозитории уже лежал чужой `_index.json` от
тестового прогона на `zvuk.md` (другой корпус, другие REQ-id). Исправлено: путь ищется от
`cases`-предка самого `target` (`.../cases/<J>` → `../suites/_index.json`); если такого предка
нет (как у `examples/`), проверка тихо пропускается, а не падает на случайных данных по соседству.
Это тот же принцип fail-closed-но-не-fail-random, что и в `review_scope.py`.

**Проверено:** эталонный пример — 0/0/0 (проверка пропущена, предка `cases` нет); реальный прогон
J01/J02/J03 — 0/0/0 (все id валидны); синтетический негативный тест (сфабрикованный `REQ-99` и
несуществующий `Вариант от`) — пойман корректно, оба правила сработали как BLOCKER.

**Почему это специфично для слабых моделей, а не общая полировка.** Стоимостная иерархия проекта
(см. «Принцип» выше) не зависит от модели — миллисекунды скрипта дешевле любого вызова агента
всегда. Но *частота* ошибок, которые скрипт теперь ловит бесплатно, растёт на слабой модели —
галлюцинация id и битая перекрёстная ссылка ближе к типичному отказу слабой модели, чем к
типичному отказу сильной. Каждая такая ошибка, пойманная линтером, а не критиком, — это разница
между «поймано за миллисекунды на шаге 1» и «поймано за 5-12 минут семантического ревью,
если критик вообще заметил» (критик — тоже модель, тоже подвержен слабости инфраструктуры).

### O-17. Точечный патч вместо `write_file` на фикс-итерациях — новая находка, сделано

Найдено при повторном разборе проекта (не из `tasks.rtf`): у `qa-designer` из инструментов
записи есть только `write_file` — целиком файл, на каждый вызов. `test-critic.md`/`review_scope.py`
уже давно решают ту же задачу с другой стороны (не перечитывать `carryForward`-кейсы), но на
стороне дизайнера её никто не решал: правило «keep diffs minimal» (`qa-designer.md`, было и
раньше) управляет тем, что меняется по смыслу, а не тем, сколько токенов стоит сам факт записи —
`write_file` всё равно требует напечатать файл целиком. При типичной находке «1 BLOCKER в одном
кейсе из пяти» (см. `result.md`, наблюдение под O-08) это близко к 100% печати ради изменения
одной строки, и так на каждой из до трёх итераций.

`run_shell_command` у `qa-designer` уже есть в списке инструментов (в отличие от
`requirements-analyst`, у которого его нет — там это не применимо). Написан
`scripts/patch_case.py`: принимает на stdin один или несколько блоков `===OLD===`/`===NEW===`,
fail-closed как `review_scope.py` — блок `OLD`, не найденный в файле ровно один раз, обрывает
**весь** вызов, ничего не записывается; при неудаче ни один из патчей вызова не применяется
(проверено: несуществующий `OLD` → код 1, неоднозначный `OLD` вроде голого `REQ-01` → код 1 с
числом совпадений в сообщении; два валидных патча в одном вызове применились точно, остальной
файл посимвольно не изменился — прогнано на эталонном кейсе).

`qa-designer.md` («Fix iterations», пункт 2) переписан: `write_file` — только для первой итерации
(файла ещё нет) или для правки настолько большой, что патч был бы просто неуклюжим `write_file`;
во всех остальных случаях — `patch_case.py`. Регенерация JSON после патча уже покрыта существующим
шагом самопроверки (`build_case_json.py` перед линтером, независимо от того, чем был отредактирован
`.md`) — отдельного правила не потребовалось.

**Ожидаемый эффект:** пропорционален доле фикс-итераций, где правки узкие (по `result.md` — типично).
Не измерено на живом прогоне — как и остальные пункты этой ветки, требует подтверждения на вашем
корпусе; в отличие от O-06/O-08 здесь эффект не может быть отрицательным или нулевым по конструкции
(патч не может стоить больше эквивалентного `write_file`, худший случай — файл переписывается почти
целиком одним патчем, что равноценно старому поведению).

## Принцип

Стоимостная иерархия проекта:

| Уровень | Порядок стоимости одного действия |
|---|---|
| Python-скрипт | миллисекунды |
| Один вызов агента | минуты, тысячи выходных токенов |
| Одна волна (P агентов + барьер) | минуты по самому медленному |
| Полный прогон | до 3 итераций × волны |

Отсюда два правила, которым подчинён весь план:

1. **Проверка, сдвинутая на уровень влево, экономит 3–4 порядка.** Всё механическое — в скрипт.
2. **Время LLM определяют выходные токены, а не входные.** Они генерируются последовательно.
   Ускорять надо печать: сокращать её объём и распараллеливать.

Дополнительный фактор среды: DeepSeek/Qwen хуже frontier-моделей держат длинные промпты с
плотностью запретов и чаще ошибаются на вложенном JSON. Это смещает приоритет в сторону
«гарантия в коде, а не в тексте промпта».

### O-13. Фаза изучения у аналитика — самое дешёвое ускорение в плане

- [ ] Предписать **одно пакетное чтение**: `read_many_files` одним вызовом на все входные файлы
- [ ] Запретить повторные обращения к исходникам — работать с прочитанным
- [ ] Поднять `max_turns` аналитика с 25 до 40
- [ ] Убрать `zvuk-sample.md` из дефолтного glob (дубль T-07 из таск-листа дефектов)
- [ ] Кэшировать `_reqindex.json` по хешу входа — пропускать шаг 0 на повторных прогонах

**«Изучение» — это три разные вещи, и только одна неустранима:**

| Что | Устранимо |
|---|---|
| Чтение файлов | ✅ сокращается до одного обращения |
| Разбор прозы — найти, где в тексте требования | ✅ выносится в скрипт (O-03) |
| Группировка в journey | ❌ **это и есть работа модели** |

**Главная причина — число обращений, а не объём.** Модели по умолчанию читают файлы по одному.
Каждое чтение — полный round trip: префилл всего накопленного контекста → генерация вызова →
результат → контекст вырос. Аналитику нужно 6 файлов (три требования, `docs/format.md`,
`GIGACODE.md`, `templates/suite-plan.md`), плюс перечитывания по ходу рассуждения.

```
последовательно:  K обращений × растущий контекст  ≈  K × C/2 работы префилла
одним пакетом:    1 обращение × C
```

При K=8 и контексте до ~25 К токенов это порядка 100 К токенов префилла против 25 К — **вчетверо
больше работы** на том же материале, и вся она тратится до того, как модель начала думать.

**Ключевой факт:** `read_many_files` **уже есть** в инструментах аналитика
(`requirements-analyst.md:6`), но спека нигде не велит его использовать — строка 33 говорит
просто «Read every requirement file», и способ выбирает модель. Правка — одна строка текста.

**Побочный эффект `max_turns: 25`.** Если 8 ходов сгорели на чтение, на индексацию, группировку
и написание N планов остаётся 17. У аналитика самый маленький бюджет ходов при самой большой
задаче (у дизайнера и писателей тестов — 40, у критика — 30).

**Чего делать не стоит: не срезать корпус для аналитика.** §3 «Бизнес-требования» — это 63 %
`zvuk.md`, и соблазн отдать только его обманчив: §1 описывает пользовательский путь, то есть
прямой материал для группировки в journey; §6 и §7 питают разделы «Зависимости и риски» и
«Выявленные пробелы». Урезав, ускорим чтение и испортим главное, ради чего аналитик существует.
Аналитик — единственный агент, которому весь корпус нужен законно; срез уместен для дизайнера
(O-09), и то с оговоркой про критика.

**Механизм — `scripts/include_skill.py`, не `!{cat}`.** Простой `cat` даёт заголовок скилла

новый документ. Для шага, который нельзя пропускать, это ровно неверное впечатление. Скрипт

### O-12. MCP-сервер поверх скриптов

- [ ] Обернуть детерминированное ядро, когда скриптов станет 5–6

```
validate_cases(path, journey?)     → {counts, findings[], blockers}
build_gate_questions(index, flags) → {gateQuestions[], lists{}, defaults{}}
gate_check(questions, answers)     → {passed, nextAction, parallel, unit}
extract_reqs(sources, prefix?)     → {reqIndex[], duplicateIds[]}
check_state(path)                  → {valid, problems[]}
```

Выигрыш не в скорости, а в **портируемости**: любой MCP-клиент получает детерминированные шлюзы
без клонирования репозитория и без Python в окружении.

**Чего в MCP не делать:** полную цепочку одним вызовом. Результат вызова уходит вызывающей
модели, и она решает, показывать ли его человеку — это ровно тот провал, против которого написан
протокол вопросов. Плюс серверу пришлось бы стать агентным рантаймом с собственным доступом к
модели.

**Отложено:** машина состояний в MCP (`e2e_next()` возвращает следующий шаг или `ask_human` и не
продвигается, пока контракт не выполнен). Идея хорошая — `gate_check.py` с его `nextAction` уже
первый её узел — но процедура за последние дни менялась трижды, фиксировать её в коде рано.
Плата: порядок фаз перестанет правиться редактированием markdown.

### Семантический поиск для ускорения цикла

**Нет.** Три причины:

1. **Не тот axis.** Семантика сокращает вход, а узкое место — выход. Вход (48 КБ) и так
   помещается в контекст.
2. **Ломает главную операцию.** Работа критика — доказательство отсутствия («не определяет ни
   одно требование»). Top-K по близости принципиально не умеет доказывать отсутствие; промах
   ретривера даёт ложный BLOCKER, то есть лишнюю полную итерацию.
3. **Есть точная адресация.** Требования пронумерованы, journey заявляет свои анкоры. Выборка по
   id даёт точность и полноту 1.0 при нуле зависимостей. Семантика была бы нечёткой версией того,
   что делается точно.

**Где уместна** (нечёткий подбор кандидатов, не проверка полноты):

- дедупликация вопросов и пробелов между journey — Фаза 3, сейчас это делает модель
- поиск противоречий в требованиях — кандидаты для суждения модели
- обнаружение пересечений между journey и между вариантами кейсов

Во всех трёх выход — список кандидатов, а не вердикт. Отдельная утилита, не часть цикла.

**Когда пересмотреть:** если придут требования без нумерации — адресовать будет нечем, и тогда
семантика незаменима.
